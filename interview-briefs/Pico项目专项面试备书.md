## 一、先看结论

Pico 不是“调用大模型再接几个工具”的演示项目，而是一个把模型的不确定输出约束为可恢复、可审计、可验证执行过程的本地 Coding Agent Harness。面试表达应始终围绕三个问题：

1. 为什么需要由 Harness，而不是模型，掌握权限、状态和完成判定？
2. 你设计了什么机制，解决长链路任务中的上下文、状态、安全和验证问题？
3. 这些机制如何通过可复现实验，而不是主观体验，证明有效？

## 四、P0 核心题：答案骨架与直接开口答案

### 1. 请用 1 分钟介绍 Pico

**答案骨架**

`场景与问题 → Harness 定位 → 三个关键机制 → 量化验证 → 岗位匹配`

**直接开口答案**

Pico 是我从零开发的本地 Coding Agent Harness，目标不是再做一个聊天界面，而是解决代码 Agent 在长链路任务里经常出现的四类工程问题：上下文不断膨胀、重复读文件、进程中断后状态丢失，以及模型没有验证就直接宣布完成。我的核心工作是把模型接入、工具调用、会话、记忆、checkpoint、skills、子任务和运行证据统一到一条受控执行链路中。上下文侧，我按生命周期分区并做压力裁剪和长结果落盘；状态侧，我用 checkpoint、文件 freshness 和 runtime identity 判断能否安全续接；执行侧，权限、读后修改、重复调用和最终完成判断都由 Harness 控制。实验中，12 组上下文配置的 Prompt 整体减少 9.31%，脚本化 E2E 的估算输入 Token 下降 14.69%，Verifier 通过率保持 100%；12 个记忆任务的重复文件读取从 60 次降为 0，固定 12 个任务的通过率、预算内完成率和 Verifier 通过率均为 100%。

**追问预判**

1. 为什么叫 Harness，而不是 Agent Framework？
2. 哪一部分是你独立设计和实现的？
3. 这些指标是真实模型还是合成模型得出的？

**危险表达**

- 不要说“完全解决了幻觉”。
- 不要把合成实验描述成线上生产成功率。
- 不要把字符压缩率和估算 Token 降幅说成 Provider 真实 usage 或账单。

### 2. Pico 一次请求的完整执行链路是什么？

**答案骨架**

`装配运行时 → 构建上下文 → 模型输出意图 → 服务端执行工具 → 记录证据与 checkpoint → 完成门禁 → 持久化`

**直接开口答案**

一次请求先由 Runtime 装配模型客户端、工作区、工具注册表、会话、记忆和权限配置。收到用户请求后，ContextOrchestrator 先刷新工作区和稳定前缀，再让 ContextManager 按 prefix、memory、relevant memory、history、current request 的顺序构建 Prompt；如果压力达到阈值，再通过 CompactManager 压缩较早历史。模型只输出工具意图或最终回答，不直接执行副作用。工具意图进入统一网关，依次经过参数、重复调用、权限和策略检查，执行后记录受影响文件、结果摘要、trace 和 checkpoint。模型提出 final 时，Final Readiness 会根据任务证据判断是否缺少验证或必需产物，必要时把任务打回。最后才更新 TaskState，保存 session、report 和事件流。因此真正控制状态转移的是 Harness，模型负责提出下一步。

**追问预判**

1. SessionStore 与 RunStore 为什么分开？
2. 工具执行失败但已经修改文件怎么办？
3. 上下文压缩发生在调用模型之前还是之后？

**危险表达**

- 不要虚构一个不存在的 `CheckpointManager`；当前 checkpoint 由 Runtime mixin 和运行流程管理。
- 不要把模型输出描述为可信命令，应该称为“待校验意图”。

### 3. 为什么模型不能自己决定权限和任务是否完成？

**答案骨架**

`概率输出不适合承担确定性约束 → 权限必须引用外部事实 → 完成必须引用执行证据 → Harness 闭环`

**直接开口答案**

因为模型的强项是生成和判断下一步，不是维护不可绕过的系统约束。即使提示词写了“修改前先读文件”，模型仍可能忘记；如果让它自己判断权限，它既是动作提出者又是审批者，无法形成安全边界。Pico 把这两类责任下沉到 Harness：工具阶段由参数校验、PermissionChecker、ToolPolicyChecker、write scope 和 sandbox 根据真实运行状态做决定；最终回答阶段由 Final Readiness 检查 TaskState 中是否存在修改、测试、必需产物和失败工具等证据。模型可以解释为什么无法验证，但不能只靠一句“已经完成”改变系统状态。这个设计的本质是把概率推理放在确定性状态机内部，让可变的模型与稳定的工程约束解耦。

**追问预判**

1. 提示词约束和程序约束分别适合什么？
2. strict、soft、warn 模式如何取舍？
3. 如果门禁误判，用户怎样继续？

**危险表达**

- 不要说模型“完全不可信”；准确说法是不能作为唯一安全边界。
- 不要声称所有门禁都是硬阻断，Final Readiness 有不同模式。

### 4. 上下文如何压缩，9.31% 和 14.69% 是怎么得到的？

**答案骨架**

`分区 → 预算与压力 → 压缩动作 → 12 组字符实验 → E2E Token 代理实验 → 指标边界`

**直接开口答案**

我没有把上下文当成一个字符串直接截断，而是按生命周期拆成稳定前缀、工作记忆、相关记忆、历史和当前请求五个区。ContextManager 按压力记录分区缩减动作，当前请求不参与普通裁剪；长工具结果写入 run artifact，Prompt 只保留受限预览、哈希和引用；压力继续升高时，再把较早历史压成结构化摘要并保留最近轮次。字符实验用短、中、长历史，低、高记忆和长、短请求组成 12 组配置，每组重复 5 次。平均原始字符数为 13520.67，渲染后为 12262，按两者计算整体减少 9.31%；逐组计算后的宏平均为 8.19%，长历史配置最高 17.56%，当前请求保留率 100%。包含工具调用的脚本化 E2E A/B 中，估算输入 Token 每任务由 9136 降至 7794，下降 14.69%，Verifier 通过率保持 100%，但它属于代理估算。随后我用 DeepSeek 对5个长会话任务复测两轮 LLM Handoff 与确定性压缩，共取得20行真实 usage。两轮配置价格中位变化分别为 -17.65% 和 -2.03%，但总输入 Token 分别增加16.33%和0.99%，累计出现3个质量退化，两轮 `claimable_cost_win` 均为 `false`。这说明真实成本结论必须同时看 usage、缓存、输出、任务成功和质量门禁，不能只挑一个下降比例。

**追问预判**

1. 为什么缩减顺序先 relevant memory？
2. 字符预算与 token 预算偏差如何处理？
3. 摘要造成信息丢失怎么办？
4. 为什么短上下文压缩率是 0？

**危险表达**

- 不要把字符压缩率与估算 Token 降幅混成一个指标。
- 不要把 `estimated_proxy` 说成真实 API 成本，也不要把 Live A/B 的中位配置价格下降单独包装成成本优化成功。

### 5. 记忆如何把重复读取从 60 次降到 0？

**答案骨架**

`首次读取沉淀 → source/freshness 绑定 → tag/关键词/时间排序 → 召回注入 → 变更失效 → 消融实验`

**直接开口答案**

Pico 的记忆分为会话内状态和跨会话 durable memory。首次读取文件后，系统把受限摘要、来源路径和 freshness 写入 working memory；后续请求会从 episodic notes 和 durable topics 中召回候选。当前实现故意采用透明规则：先比较 tag 精确命中，再比较查询与文本、来源的关键词重叠，最后用时间和 note index 排序。召回结果还要经过陈旧性和安全检查；文件内容变化时，对应摘要会失效，避免旧知识覆盖新代码。实验设置了 12 个事实查询、编辑依赖和历史引用任务，每个重复 5 次。关闭记忆或注入无关记忆时都发生 60 次额外读取，启用相关记忆时为 0；平均模型尝试从 2 次降到 1 次，第二阶段平均额外工具步骤从 1 降到 0，正确率仍为 100%。它证明的是受控任务上的依赖关系，不代表任意代码检索都不需要重新读文件。

**追问预判**

1. 为什么不用 embedding？
2. freshness 如何计算？
3. 召回到恶意或含密钥的记忆怎么办？
4. 关键词规则对同义词效果差怎么解决？

**危险表达**

- 不要说系统自动抽取了所有函数签名；当前实现主要保存受限结果摘要和结构化 note。
- 不要说“完整任务工具调用为 0”，只是后续问答阶段的额外工具步骤为 0。

### 6. checkpoint / resume 如何识别过期状态？

**答案骨架**

`checkpoint 内容 → 恢复时三类校验 → 状态分类 → 安全处理 → 10 个任务、30 次运行`

**直接开口答案**

Pico 的 checkpoint 保存任务目标、已完成项、下一步、关键文件 freshness、TaskState 和 runtime identity。恢复时不会直接把旧状态覆盖到当前环境，而是依次检查 checkpoint schema、关键文件是否变化，以及 cwd、模型客户端、审批策略、feature flags、工作区指纹和工具签名等 runtime identity。完全一致时标为 full-valid；关键文件变化时标为 partial-stale，并使相关文件摘要失效；运行身份不一致时标为 workspace-mismatch；schema 不兼容则拒绝信任。实验包含 10 个任务，每个重复 3 次，共 30 次运行；启用机制后 27 次恢复成功，成功率为 90%，6 次工作区漂移全部识别，错误接受为 0。这里最重要的不是追求 100% 强行恢复，而是宁可暴露不一致，也不在错误环境里静默续跑。

**追问预判**

1. 90% 中失败的那一类是什么？
2. 为什么同时需要文件 freshness 和 workspace fingerprint？
3. 模型从 A 换到 B 是否一定不能恢复？
4. checkpoint 在什么时机创建？

**危险表达**

- 不要说系统会自动回滚代码；当前重点是检测、标记和安全续接。
- 不要说只校验 Git commit，实际 runtime identity 更广。

### 7. 工具调用经过哪些安全门禁？

**答案骨架**

`工具存在 → 参数/路径 → 重复调用 → 权限 → 使用策略 → 沙箱执行 → 前后快照 → 证据记录`

**直接开口答案**

所有工具都经过统一 `run_tool` 网关。第一步确认工具存在并校验参数，路径解析在工具 Schema 和工作区解析层阻止越界；第二步拦截完全相同的重复调用，避免模型陷入循环或重复副作用；第三步由 PermissionChecker 根据只读模式、审批策略、Plan Mode 和 worker write scope 决定是否授权；第四步由 ToolPolicyChecker 执行“修改已有文件前必须有 fresh read”等规则，并限制用 shell 绕过专用搜索工具。通过后才真正执行。对高风险工具，执行前后都会抓取工作区快照，即使命令非零退出但已经改了文件，也会记录为 partial success，而不是简单当作无副作用失败。最后写入 affected paths、diff summary、security event 和 trace。安全实验覆盖 10 个场景、30 次运行，但我只把它称为受控场景验证，不称为完整安全证明。

**追问预判**

1. 参数校验是否使用 Pydantic？
2. 为什么 shell 搜索要被限制？
3. 命令失败却改了文件如何恢复？
4. sandbox 在 macOS 和 Linux 上能力是否一致？

**危险表达**

- 不要把所有参数校验都归功于 Pydantic；工具有自己的 Schema 与验证逻辑。
- 不要说沙箱能阻挡所有系统调用；best-effort 与 required 的保证不同。

### 8. Agent 没验证就结束的问题怎么解决？

**答案骨架**

`问题 → TaskState 证据 → readiness reasons → 多模式决策 → 打回闭环 → 局限`

**直接开口答案**

模型经常把“生成了修改方案”误当成“任务已经完成”，所以 Pico 不直接接受 `<final>`。Engine 收到最终回答后，先运行 before-final hooks，再调用 Final Readiness。它根据 TaskState 中的工具轨迹、修改路径、测试或验证证据、必需产物以及失败状态生成结构化 reasons。在 soft 模式下，第一次发现问题会向模型注入 runtime notice，让它继续补验证；strict 模式遇到 hard reason 会阻断 final；warn 模式则允许完成但保留风险记录。这样完成判定从一句自然语言变成了可审计的状态转换。设计上我没有要求所有任务都必须跑 pytest，因为文档问答和代码修改的验证要求不同；门禁需要结合任务类型和证据严重程度，否则会把质量治理变成僵硬流程。

**追问预判**

1. 如何判断“需要测试”？
2. 模型第二次仍不验证怎么办？
3. 哪些原因属于 hard reason？
4. 如何防止无限打回？

**危险表达**

- 不要说所有 final 都会被阻断。
- 不要把 Final Readiness 描述成另一个 LLM Judge；它主要基于结构化运行证据。

### 9. 12 个任务 100% 能说明什么，不能说明什么？

**答案骨架**

`评测对象 → 三项指标 → 确定性设计 → 能证明 → 不能证明 → 下一步`

**直接开口答案**

这组 benchmark 的目标是验证 Harness 的确定性工程能力，而不是给底层模型做通用代码能力排名。12 个任务覆盖 documentation、durable contract、recovery、text edit 和 tool boundary 五类，每个任务都有固定 fixture、允许工具、step budget 和独立 verifier。通过不仅要求模型返回 Done，还要求目标文件真实存在或内容满足断言，同时必须在预算内结束。结果是 12 个任务全部通过、全部在预算内、12 个 verifier 全部通过。为了减少模型随机性，使用 Scripted/FakeModelClient 和固定解码配置，所以它很适合 CI 回归，能证明状态机、工具边界和工件协议在这些场景下稳定；但它不能证明面对真实仓库、开放问题和不同模型时仍然 100% 成功。下一步应增加真实 provider 的重复实验、难度分层、置信区间和失败分类。

## 五、P1 深挖题：回答要点

### 10. 长工具结果为什么落盘，而不是直接截断？

- 直接截断会永久丢失尾部信息；落盘可以让 Prompt 保持短，同时保留完整证据。
- 当前默认内联上限为 1000 字符，超出后写入 run artifact，并返回受限预览、相对引用和内容哈希。
- 代价是后续需要再次读取工件，而且工件存储需要权限、生命周期和敏感信息治理。

**直接开口答案**

长工具结果的核心矛盾是 Prompt 预算和信息保真不能同时靠“全部内联”解决。Pico 对普通工具结果设置 1000 字符的内联上限，超出后把完整内容写入当前 Run 的 artifact，模型侧只收到相对引用、受限预览和内容哈希。这样历史不会被一次日志或大文件读取撑爆，但排障时仍能回到完整证据。相比直接截断，它把“现在不放进上下文”和“永久丢弃信息”分开了。代价是模型如果确实需要尾部细节，还要再次读取工件；同时 artifact 自身也必须经过脱敏、路径约束和生命周期治理，所以它是预算与可审计性的折中，不是无成本优化。

**追问预判**

1. 为什么是 1000 字符，而不是根据模型窗口动态计算？
2. 工件引用失效或文件被删除怎么办？
3. 超长输出中包含密钥时在哪一层脱敏？

### 11. 为什么记忆不用向量数据库？

- Pico 当前是单机、本地、小规模记忆，优先目标是透明、可调试和零外部依赖。
- tag、关键词、时间排序能直接解释“为什么召回”，文件 freshness 也容易和来源绑定。
- 局限是同义词和语义迁移能力弱；数据量增大后，可把 embedding 作为候选召回层，但仍保留 freshness、安全过滤和确定性 rerank。

**直接开口答案**

我没有默认引入向量数据库，是因为 Pico 当前面对的是单机、小规模、强来源约束的代码记忆，首要目标是正确、透明和可调试，而不是海量语义检索。现有召回先看 tag 精确命中，再看关键词重叠和时间顺序，并把 note 与来源路径、freshness 绑定；面试或排障时可以直接解释为什么召回、为什么拒绝。向量检索擅长同义表达，但相似度高不等于代码事实仍然有效，也不能替代陈旧性和安全检查。当前方案的短板是语义泛化弱。规模扩大后，我会用 embedding 做候选召回，再用 freshness、权限、来源可信度和确定性规则 rerank，而不是让向量分数直接决定进入 Prompt 的内容。

**追问预判**

1. 关键词检索如何处理中英文和代码符号？
2. 什么时候数据规模足以值得引入向量库？
3. 向量召回结果如何做权限过滤？

### 12. 为什么不直接基于 LangGraph？

- 不要回答“LangGraph 不好”，而要回答研究目标不同。

- 如果目标变成复杂业务工作流、团队协作和生产级持久化，LangGraph 的图状态、生态和可观测集成可能更合适。

**直接开口答案**

我选择自研并不是因为 LangGraph 不好，而是 Pico 的研究对象本身就是 Harness 边界：Prompt 每一段如何排列、工具副作用如何记录、checkpoint 如何判断过期、final 如何依据证据通过，这些都需要细粒度控制。如果先套用框架，我仍然要深入改造其状态和执行语义，反而不利于做小而可验证的消融实验。自研让我能用纯 Python 明确每次状态转换和工件协议，代价是要自己承担并发、持久化、可观测和生态集成。若场景变成固定业务图、团队协作、分布式执行或需要成熟 tracing，我会重新评估 LangGraph，而不是把“自研”当作长期不可改变的目标。

**追问预判**

### 13. 子 Agent 如何防止越权和写冲突？

- 子任务有独立 WorkerTask、状态和通知；主 Agent 负责生命周期管理。
- `write_scope` 进入权限检查，写路径不在范围内时拒绝。
- 目前重点是路径级隔离和受控派发，不应夸大为完整事务隔离；并发写同一逻辑资源仍需更强的锁、合并或 worktree 方案。

**直接开口答案**

Pico 为每个子任务创建独立 WorkerTask 和子 Runtime。Explore Agent 强制只读，普通 Worker 没有 `write_scope` 时同样只读；有 scope 时，目标路径必须经过权限检查，越出范围直接拒绝。Worker 使用独立模型客户端执行，状态、工具步数、耗时和产物回写到父 Session，并通过通知队列交给主 Agent。这个设计能解决“谁能写哪些路径”的越权问题，但不能保证两个 Worker 修改不同文件时不存在逻辑冲突，也不是数据库事务隔离。当前最安全的用法是给子任务划分不重叠写域。进一步并发化时，应加入 worktree、基于 patch 的合并、冲突检测和主 Agent 提交门禁。

**追问预判**

1. Explore 和 Worker 的权限具体有什么不同？
2. Worker 已经开始执行后如何停止？
3. 两个 scope 不重叠为什么仍可能逻辑冲突？

### 14. Prompt 前缀缓存如何保持稳定？

- 把系统规则、工具描述和相对稳定的工作区信息放在 prefix，把当前请求和动态历史放在尾部。
- prefix 通过内容哈希形成 cache key；工作区或工具签名变化时主动刷新。
- 需要区分“前缀结构稳定”与“provider 实际命中缓存”，后者依赖模型服务返回的 usage 元数据。

**直接开口答案**

前缀缓存的关键不是“给 Provider 传一个 cache 参数”，而是让 Prompt 头部尽量稳定。Pico 把系统规则、工具说明、运行模式、Skills 摘要和工作区信息组织为 prefix，把频繁变化的会话历史和当前请求放在后面，并对 prefix 计算内容哈希作为 cache key。工作区指纹、工具签名或运行模式变化时主动刷新，避免错误复用。Provider 适配层再把不同接口返回的 cached tokens、cache hit 和 usage 归一化到同一元数据。这里必须区分结构稳定率与真实缓存命中率：前者由 Harness 控制，后者还取决于 Provider 的缓存规则，不能只凭哈希不变就宣称已经命中。

**追问预判**

1. Skills 变化为什么会影响前缀？
2. 工作区信息太动态时如何避免频繁失效？
3. 怎么证明缓存真的节省了 token 或延迟？

### 15. 项目最真实的一次失败和复盘是什么？

### 16. Skills 如何发现、覆盖、隔离并执行？

**答案骨架**

`发现顺序 → 元数据解析 → Prompt 可见性 → 执行上下文 → 工具/模型隔离 → 事件审计`

**直接开口答案**

Pico 的 Skill 是可发现、可约束的工作流单元，不只是把一段文本拼进 system prompt。启动时先加载内置 Skills，再扫描用户目录 `~/.pico/skills`、项目 `skills/` 和 `.pico/skills/`；后加载的同名 Skill 会覆盖前面的定义，因此项目可以定制全局行为。每个 Skill 从 frontmatter 解析名称、描述、是否允许用户调用、执行上下文、允许工具、模型覆盖和路径提示。执行时支持 inline 和 fork：inline 复用当前 Runtime，fork 创建隔离子 Runtime；如果声明 `allowed_tools`，系统临时切换到 Skill 专属 Tool Profile，结束后恢复；声明模型时也只在上下文管理器内临时覆盖。调用、完成、子会话和答案长度都会写事件。风险是项目仓库中的 Skill 本身属于不可信输入，生产化还需要来源签名、显式授权和更严格的路径隔离。

**追问预判**

1. 同名 Skill 的真实覆盖顺序是什么？
2. fork 为什么不直接使用 WorkerManager？
3. Skill 声明一个不存在的工具会怎样？
4. 如何防止恶意仓库 Skill 注入指令？

**危险表达**

- 不要说所有 Skill 都在启动时完整注入 Prompt；Prompt 主要展示可用摘要，执行时才展开正文。
- 不要说 `allowed_tools` 会增加权限，它只会从现有工具中进一步收缩。

### 17. 如何统一 OpenAI-compatible 与 Anthropic-compatible Provider？

**答案骨架**

`ProviderConfig → protocol 选择适配器 → complete 统一边界 → usage 归一化 → 重试与错误分类 → 能力路由`

**直接开口答案**

Pico 把 Provider 名称、传输协议和模型能力分开。配置先解析为 `ProviderConfig`，其中 `name` 表示用户选择的 profile，`protocol` 决定使用 OpenAI-compatible 还是 Anthropic-compatible 客户端，因此 DeepSeek profile 也可以走 Anthropic 协议。两个客户端最终都暴露统一的模型完成边界，并把文本、input/output tokens、cached tokens、重试次数等归一化，Runtime 不需要理解不同响应结构。网络层只对 408、409、425、429 和 5xx 等可重试状态及传输错误做有限重试；失败后抛出结构化 `ProviderError`，URL 会去掉认证信息，body 只保留受限摘要。图像请求再通过 ModelClientRouter 路由到主模型或独立 vision provider。这个抽象统一的是 Harness 需要的最小能力，不假设各家所有高级功能完全等价。

**追问预判**

1. 为什么 Provider profile 和 protocol 不能合并成一个字段？

3. 重试如何避免重复计费或副作用？
4. Provider usage 字段不一致怎么处理？

**危险表达**

- 不要说所有 Provider 都支持同一套 Prompt Cache 或多模态能力。
- 不要说任何错误都会自动重试。

### 18. Session、Run、Trace 和 Report 为什么分开存储？

**答案骨架**

`恢复状态与审计证据分离 → Session 快照 → Run 工件 → JSONL 事件 → Report 汇总 → 原子性`

**直接开口答案**

Pico 把“下次继续任务需要什么”和“这次运行发生了什么”分成两条存储轨道。Session JSON 保存会话历史、记忆、checkpoint、todos 和 workers 等可恢复状态，并配有 session event JSONL；每次用户请求又创建独立 Run 目录，保存 `task_state.json`、`trace.jsonl`、`report.json` 和大工具输出。TaskState 是运行中的状态快照，trace 是按时间追加的细粒度事件，report 是结束后的汇总视图。Session 和结构化 JSON 采用临时文件加 replace 的原子写，避免留下半截 JSON；trace 使用追加写，适合流式事件，即使进程中断也能保留已发生部分。分离后 Resume 不必加载所有调试日志，评测和排障也不会依赖一份不断膨胀的会话文件。

**追问预判**

1. JSONL 追加是否保证每条事件绝对不丢？
2. TaskState 和 Report 中存在重复字段，如何避免不一致？
3. 为什么当前阶段不使用 SQLite？
4. Run 和 Session 的 ID 如何关联？

**危险表达**

- 不要把文件系统原子替换描述成跨机器事务。
- 不要说 trace 与 Session 是强一致事务，当前实现主要保证可追溯和局部原子性。

### 19. Pico 从 MVP 演进到当前架构经历了什么？

**答案骨架**

`最初最小闭环 → 暴露的工程问题 → 三次边界重构 → 评测驱动稳定 → 当前局限`

**直接开口答案**

我会把 Pico 的演进概括为三个阶段。第一阶段先完成最小闭环：模型产生工具调用，Runtime 执行并返回结果；这验证了可用性，但状态、权限和日志耦合在一起，长任务很难恢复。第二阶段把 Session、TaskState 和 Run 工件拆开，并引入统一工具网关、checkpoint 和事件流，让执行过程可恢复、可审计。第三阶段针对实际长链路问题加入 ContextOrchestrator、工具结果工件化、分层记忆、Final Readiness、Plan Mode 和受控 Worker。每次重构都不是因为类太大，而是先用失败场景暴露边界，再用 benchmark 和 ablation 固化行为。我的主要贡献是定义这些状态边界、实现治理链路并建设验证工件。当前不足是核心指标仍以确定性合成实验为主，真实模型和多进程并发覆盖还不够。

**追问预判**

1. 哪次重构成本最高？
2. 如何保证重构没有改变已有行为？
3. 如果只保留三个模块，你保留什么？
4. 哪个设计现在看来最需要推倒重来？

**危险表达**

- 面试前必须用自己的真实开发时间线替换“三阶段”细节，不能把建议叙事冒充真实经历。
- 不要把所有文件都说成自己一次性独立完成，要能对应具体提交或实现。

## 六、P2 源码级深挖题

### 20. Plan Mode 与 TodoLedger 如何防止复杂任务失控？

**回答要点**

- Plan Mode 是持久化运行模式，不只是 Prompt 中的一句话；进入后会保存 session、切换 `plan` Tool Profile 并刷新前缀。
- 计划文件只能位于 `.pico/plans/`，写操作只能针对当前 plan artifact；只允许 Explore 子 Agent，不允许可写 Worker。
- 退出前要求 plan artifact 存在且非空。TodoLedger 独立保存 `pending / in_progress / done / blocked` 状态、优先级、备注和变更事件。
- 两者分工不同：Plan Mode 约束当前能做什么，TodoLedger 记录任务拆解进度。当前 Todo 状态本身不强制验证完成真实性，还需要 Final Readiness 和工具证据配合。

**追问预判**

1. 为什么计划必须落盘，不能只留在上下文？
2. Plan Mode 如何阻止通过 shell 间接写业务文件？
3. Todo 标记 done 是否等于任务真的完成？

**危险表达**

- 不要把 TodoLedger 描述为完整工作流引擎。
- 不要说 Plan Mode 绝对阻止所有旁路，仍需结合工具实现与沙箱验证。

### 21. 长期记忆如何防止污染，Auto-Dream 如何并发运行？

**回答要点**

- Durable promotion 只在用户表达明确记忆意图时从最终回答中抽取，并拒绝空内容、密钥形态、临时任务状态、stdout/stderr 和过长噪声。
- `memory_quarantine.py` 识别提示注入标记与 secret pattern；检索时还会做 evidence staleness 检查。
- Auto-Dream 先按时间和新 Session 数量过 gate，再获取 memory lock；获取失败直接以 `lock_held` 跳过，不阻塞主请求。
- Dream 在后台 daemon thread 中启动受限子 Runtime，只允许写 memory scope；完成后记录 changed files 和 dream report，失败时恢复锁时间并写审计事件。
- 当前锁是本地文件加 PID/mtime 的轻量协调，不是严格的分布式锁，仍存在进程竞争和 TOCTOU 边界。

**追问预判**

1. 为什么不能让模型自动决定所有内容都进入长期记忆？
2. 旧锁怎样判断持有进程已经失效？
3. Dream 写坏 memory 文件如何恢复？
4. Prompt injection 为什么会进入记忆系统？

### 22. Worker 的 spawn、continue、stop 和结果回传如何实现？

**回答要点**

- `WorkerManager` 为每个任务创建 `WorkerTask`，记录类型、write scope、子 Runtime、线程和 stop flag。
- 有 `model_client_factory` 时后台线程执行，否则同步执行；`continue_task` 复用活跃子 Runtime，而不是创建一个失去上下文的新 Agent。
- `stop_task` 设置 stop flag 并调用子 Runtime 的 abort；状态先进入 `stopping`，线程实际结束后再成为 `stopped`。
- 执行结束收集 result、tool steps、attempts、duration 和工件，通过线程安全 Queue 发送通知，主 Runtime drain 后标记已消费。
- 当前线程模型共享进程资源，隔离边界弱于进程或容器；模型客户端、文件系统和第三方库的线程安全必须单独考虑。

**追问预判**

1. 为什么继续任务必须复用同一个子 Runtime？

4. 为什么 Explore Agent 使用 `approval_policy=never`？

### 23. API Key 如何避免进入 Prompt、Trace 和 Report？

**回答要点**

- Runtime 根据显式 `secret_env_names` 和 `API_KEY / TOKEN / SECRET / PASSWORD` 等名称标记环境变量。
- `redact_text` 按秘密值长度降序替换，避免短值先替换破坏长值匹配；`redact_artifact` 递归处理 dict、list、tuple 和字符串。
- Report 和部分工件写入前调用 redaction；shell 环境采用 allowlist，只传允许变量、`PWD` 和必要的 `PATH`。
- Provider URL 通过 `sanitize_url` 去掉认证信息、query 和 fragment；错误 body 只保留受限摘要。
- 边界：未知格式、编码后密钥、分片输出、文件内凭据和工具自行持久化仍可能绕过基于值替换的脱敏。

**追问预判**

1. 如果密钥只出现一半还能识别吗？
2. 为什么既按变量名又按变量值脱敏？
3. Trace 追加写之前还是之后脱敏？
4. 如何测试日志中不存在真实密钥？

### 24. 为什么使用 `<tool>` / `<final>` 文本协议，解析失败怎么办？

**回答要点**

- Pico 选择一个 Provider 无关的最小文本协议：模型返回一个或多个 `<tool>`，或一个 `<final>`；工具体支持 JSON 和受限 XML 形式。
- Parser 只负责把文本转成“工具意图 / 最终回答 / retry”，真正的工具存在性、参数、权限和策略在网关层验证。
- 空响应、缺少标签、非法 JSON、空工具列表或错误 args 类型都会生成 retry notice，让模型重新输出；不把不可执行文本当成成功。
- ProviderError 属于另一条错误路径：HTTP/网络错误先有限重试，最终失败后记录结构化错误、checkpoint、trace 和用户可理解的停止原因。
- 取舍：文本协议跨 Provider、易回放，但比原生 function calling 更依赖模型遵循格式，也需要防止标签混淆和转义问题。

**追问预判**

1. 为什么不直接使用 OpenAI function calling？
2. 同时出现 `<tool>` 和 `<final>` 时优先什么？
3. 连续格式错误如何防止无限重试？
4. 模型输出多个工具时是串行还是并行？

### 25. 文件状态如何保证原子性和并发一致性？

**回答要点**

- Session 保存先写带 PID 和线程 ID 的临时文件，再通过 `os.replace` 原子替换，并在进程内用 `threading.RLock` 串行化。
- TaskState 和 Report 使用 `NamedTemporaryFile` 后 replace；避免异常时留下半截 JSON。
- Trace 是 JSONL 追加写，优点是中断后保留已有事件，缺点是它与 Session/Report 不是跨文件事务。
- Memory 有独立锁文件协调 Auto-Dream；WorkerManager 用互斥锁保护状态列表，用 Queue 传递跨线程通知。
- 当前保证主要是单机进程内和单文件原子性；多进程同时写、网络文件系统、磁盘满、最后一条 JSONL 未刷盘等情况仍需 WAL/SQLite 或数据库事务。

**追问预判**

1. `os.replace` 为什么比直接 `write_text` 更安全？
2. JSONL 最后一行损坏时怎么恢复？
3. RLock 能否保护另一个 Pico 进程？
4. 为什么 Memory 锁和 Session 锁使用不同机制？

### 26. Tool Profile 如何动态收缩不同运行模式的能力面？

**回答要点**

- 工具先注册成完整集合，再生成 `default / plan / dream / readonly / worker` 五类 `ToolSetProfile`。
- Readonly 只保留只读工具并移除协调、模式切换和交互工具；Worker 不具备协调其他 Agent、切换模式、交互询问和 shell 能力。
- Plan、Dream 按工作流增加极少量写工具，真正写入路径还要继续通过 PermissionChecker 和 write scope。
- Skill 声明 `allowed_tools` 时动态创建临时 `skill:<name>` Profile，只取“Skill 声明集合 ∩ 当前真实工具集合”。
- Tool Profile 是能力面第一层，不替代参数校验、审批、策略和沙箱。

**追问预判**

1. 为什么 Worker 默认不能使用 shell？
2. Profile 切换后 Prompt 中的工具说明如何同步？
3. Tool Profile 与 RBAC 有什么区别？

### 27. LLM Handoff 摘要失败时如何保证任务还能继续？

**回答要点**

- Tier 3 压力且新增历史足够时，ContextOrchestrator 可以触发 LLM handoff；输入是受限 conversation delta 和 prior summary。
- Handoff 要求结构化输出 Goal、Constraints、Files、Decisions、Blockers、Next Steps；Goal 和 Next Steps 缺失即判无效。
- Provider 异常、解析失败或字段不完整时，Adapter 返回 `None`，CompactManager 回退到 deterministic summary，而不是中断主任务。
- 摘要保存 last included event boundary，后续只处理增量，避免反复总结全部历史。
- 风险仍是语义丢失，因此关键文件路径、错误信息、约束和下一步必须进入结构化字段，并需要独立的 handoff 质量评测。

**追问预判**

1. 为什么 LLM 摘要不是唯一方案？
2. prior summary 如何避免越滚越错？
3. 如何检测摘要漏掉关键约束？
4. Handoff 调用的 token 成本如何记录？

## 七、P3 低频工程与选型题

### 29. 为什么选择 Textual TUI，而不是 Web UI？

**参考回答**

Pico 的核心使用场景在本地仓库和终端，Textual 可以直接复用同一个 Runtime、Engine generator、审批回调和 slash command，不需要额外引入前后端协议、浏览器权限和部署服务。TUI 只承担展示层：工具卡片、状态栏、输入历史和审批交互，业务状态仍在 Runtime。代价是远程协作、富文本和多用户能力有限；如果进入团队服务形态，Web UI 会更合理。

**追问**：TUI 如何避免阻塞事件循环？审批回调为什么使用线程事件？TUI 和 REPL 如何保证行为一致？

### 30. 多模态图片如何进入模型，又如何避免污染文本历史？

**参考回答**

图片加载后转换成带 path、mime type、bytes 和 sha256 的 `ImageBlock`，与文本组成 `ModelInput`。ModelClientRouter 根据 `image_count` 选择主模型或独立 vision provider，适配器在最后边界才转换为 OpenAI data URL 或 Anthropic base64 block。历史和 trace 不保存大段 base64，只记录媒体元数据和 Run artifact 引用，从而控制体积并保留审计能力。

**追问**：图片大小和格式如何限制？Vision 超时如何处理？为什么不把 base64 写进 Session？

### 31. Provider 配置优先级为什么这样设计？

**参考回答**

Pico 使用“CLI 显式参数 > 环境变量 > 项目 `.pico.toml` > 全局配置 > 代码默认”的优先级。默认配置保证开箱结构完整，全局配置复用个人偏好，项目配置固定仓库差异，环境变量适合秘密和 CI，CLI 适合一次性覆盖。解析结果最终收敛到不可变 `ProviderConfig`，避免下游模块各自读取环境变量产生不一致。

**追问**：项目 `.env` 是否安全？显式 config path 如何参与优先级？如何输出最终配置又不泄密？

### 32. 这个项目体现了哪些 Python 工程设计能力？

**参考回答**

我主要使用 dataclass 表达 TaskState、WorkerTask 和不可变配置，用组合和小型 mixin 拆分 Runtime 的 checkpoint、secret 等横切能力；用 context manager 保证 Skill 的模型和工具覆盖一定恢复；用 generator 输出运行事件；用线程、RLock 和 Queue 处理 TUI、Worker 与后台 Dream。重点不是用了哪些语法，而是每种机制都对应清晰的生命周期和失败边界。

**追问**：为什么部分状态使用 dict 而不是 dataclass？线程模型受 GIL 什么影响？异常跨线程如何传播？

### 33. Pico 的跨平台与打包限制是什么？

**参考回答**

项目要求 Python 3.10+，使用 setuptools 构建、uv 管理开发依赖，Python 3.10 通过 tomli 兼容 TOML。纯 Python Runtime、TUI 和文件存储较容易跨平台，但强沙箱能力依赖操作系统后端，例如 Linux bubblewrap；macOS 或缺失后端时只能使用不同程度的 best-effort。路径解析、shell 语义、文件锁和 `os.replace` 在网络文件系统上的保证也需要分别验证。

**追问**：为什么不打包成单文件二进制？Windows shell 如何适配？沙箱不可用时 required 模式怎么处理？

### 34. 如何把本地 Harness 演进为团队或生产服务？

**参考回答**

我不会直接把当前 Runtime 套一层 HTTP API 就称为生产化，而会先重新定义租户、任务和工件边界。会话状态进入事务数据库，大工件进入对象存储，Worker 经队列派发到隔离执行环境，权限改为服务端策略与短期凭据，事件统一进入可查询的 tracing 系统。同时保留本地模式作为开发和故障复现入口。最大的变化不是 UI，而是从单用户可信工作区转向多租户不可信输入。

**追问**：如何设计任务幂等？用户取消如何传播？本地文件和远程仓库如何同步？

## 八、连续追问训练

### 链路 A：围绕上下文压缩

**面试官：为什么 Prompt 整体只减少 9.31%，是不是效果一般？**

回答：12 组矩阵包含四组短历史配置，这些配置没有达到缩减条件，所以压缩率为 0；中等历史约为 7.08% 到 7.22%，长历史约为 17.27% 到 17.56%。按平均字符数计算的整体降幅是 9.31%，逐组压缩率的宏平均是 8.19%。我更关注“只在有压力时压缩”和“当前请求保留率 100%”，而不是为了更高数字无条件删除信息。

**面试官：那回答质量有没有下降？**

回答：12 组字符压力矩阵只验证长度和当前请求保留，不能单独证明语义质量无损。另一组脚本化 E2E A/B 的成功率和 Verifier 通过率都保持 100%，质量退化数为 0，但它仍是受控脚本实验，不代表真实模型在复杂任务上没有退化。下一步应加入真实模型重复采样和更强语义 verifier。

**面试官：为什么不用模型上下文窗口的 token 数直接裁剪？**

回答：运行时已经有估算 token 和 provider context window 用于 pressure tier，字符矩阵保留字符指标是为了跨 Provider 可复现；脚本化成本 A/B 单独报告估算输入 Token。DeepSeek Live A/B 两轮已取得20行真实 usage，但配置价格中位降幅从17.65%波动到2.03%，总输入 Token 两轮均增加，并累计出现3个质量退化。因此14.69%仍只能称为脚本化代理降幅，而真实实验结论是当前 LLM Handoff 尚未形成稳定、可声明的成本收益。

### 链路 B：围绕记忆实验

**面试官：模型不读文件也能答对，会不会只是把答案泄漏到 Prompt？**

回答：记忆的目的本来就是把第一次读取后的受控摘要注入后续 Prompt，因此“信息进入 Prompt”不是泄漏，而是实验变量。关键是 memory-off 和 irrelevant-memory 组使用相同任务，必须再次读取才能答对；memory-on 组依赖相关记忆直接回答。为了避免评测污染，每个任务使用隔离 fixture，并检查初始记忆为空。

**面试官：真实代码变化后，旧摘要不会害你吗？**

回答：摘要带来源和 freshness。构建上下文和恢复状态时会重新检查文件，新鲜度不一致会使摘要失效并记录 stale path，迫使系统重新读取。这个机制比单纯依赖向量相似度更重要，因为相似不代表仍然正确。

**面试官：为什么正确率都是 100%，这个任务是否太简单？**

回答：是的，它是依赖性消融实验，故意把模型能力难度降到最低，只验证“有无相关记忆是否改变重复工具调用”。它不用于证明复杂代码理解能力。下一阶段需要增加跨文件依赖、同义表达、冲突记忆和时间变化等挑战集。

### 链路 C：围绕安全网关

**面试官：有 sandbox 为什么还需要审批和工具策略？**

回答：三者解决不同层次的问题。审批决定用户是否授权副作用，策略约束调用顺序和语义，例如读后修改，sandbox 限制命令获得授权后在操作系统层能做什么。任何单层都不足以覆盖另外两层。

**面试官：命令返回非零，但已经改了文件怎么办？**

回答：网关在高风险工具前后抓取工作区快照。如果非零退出且 workspace changed，会标记 partial success，记录 affected paths 和 diff summary，后续不能按普通失败假设“什么都没发生”。

**面试官：你的 10 个安全场景能证明系统安全吗？**

回答：不能。它只能证明已枚举场景的控制逻辑按预期工作。完整安全评估还需要命令解析绕过、符号链接、TOCTOU、平台差异、资源耗尽、秘密外泄和恶意仓库内容等对抗测试。

## 十、个人素材缺口

1. **真实模型重复采样仍不足**：DeepSeek Live A/B 已完成两轮，共10个配对、20行真实 usage；两轮均未通过成本收益门槛，累计出现3个质量退化。下一步应先修复 `multi-file-refactor` 的 Handoff 退化和 `add-endpoint-with-test` 的稳定失败，再补至至少3轮并报告置信区间。
2. **90% 恢复率的失败样本**：当前失败样本是 `schema_mismatch_missing`，它没有可用 checkpoint，系统返回 `no-checkpoint` 和 `missing recovery state`。这应解释为安全拒绝而不是静默恢复失败；面试时使用“10 个任务、30 次运行中恢复成功率 90%”，不要包装成生产故障覆盖率。
3. **个人开发过程**：准备一个最初错误设计、一次定位过程和一次重构决策，避免项目听起来像一次性完美设计。
4. **规模信息**：准备代码规模、测试数量、开发周期和主要版本演进，但必须现场从仓库统计后再使用。
5. **用户价值**：目前指标偏 Harness 内部效率；若有真实使用记录，补充完成一个长链路任务节省多少人工步骤或时间。
6. **安全边界**：明确不同平台的 sandbox 能力，以及 best-effort 模式不提供哪些保证。
