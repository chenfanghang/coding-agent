# Pico v3 项目架构深度解析说明

本文为 `pico v3` 版本的官方架构设计规范文档，详细说明 Pico 的系统概述、设计原则、两条主执行链路、模块职责图谱、10 阶段运行生命周期与工件持久化机制。

---

## 1. 系统概述与工程定位 (Overview & Positioning)

`pico v3` 是一个运行在本地 Git 代码仓库中的轻量级 **Local Coding Agent Harness**。它并非简单的聊天终端，而是一个具备工作区指纹感知、受控工具网关、完成治理门禁 (Final Readiness)、分层记忆检疫 (Quarantine) 和运行审计工件的自动编程助手。

### 核心工程使命：
- **开发过程受控化**：通过 ToolProfile 限制工具暴露面，防止 Shell 危险命令与未经验证的死循环。
- **状态恢复确定化**：通过原子状态镜像与 Git Commit SHA/Hash 漂移校验，支持高可靠的会话断点恢复。
- **上下文成本最优化**：通过 `ContextOrchestrator` 编排静态 Prefix，实现大模型前缀缓存 (Prompt Caching) **85%+ 高命中率**。
- **验证就绪硬门禁**：通过 `FinalReadiness` 治理逻辑，解决 Agent 改完代码不验证就急于答复的盲目退出痛点。

## 2. 架构设计哲学与四项基本原则 (Design Principles)

在设计 Pico v3 时，我们从第一性原理拆解了通用 LangChain / AutoGPT 框架在本地 Coding 场景下的四大核心矛盾并确立了解法原则：

```text
+-----------------------------------------------------------------------------------+
|                            Pico v3 四大工程矛盾与解法原则                         |
+-----------------------------------------------------------------------------------+
| 矛盾 1: 上下文爆炸与 Token 费用高昂  ===> 解法: ContextOrchestrator + Prompt Caching|
| 矛盾 2: 模型提早盲目退出 (Premature Exit)===> 解法: FinalReadiness 完成治理硬性门禁|
| 矛盾 3: 坏记忆与幻觉污染长期数据库  ===> 解法: MemoryQuarantine 检疫隔离池       |
| 矛盾 4: 高危 Shell 与盲改破坏仓库  ===> 解法: Read Freshness Guard + Shell 沙箱  |
+-----------------------------------------------------------------------------------+
```

## 3. 总体架构与两条主线 (Setup Line & Execution Line)

Pico v3 的整体系统运作可以被精准拆解为两条核心主线：

```text
===================================================================================
1. 装配线 (Setup Line): CLI -> Config -> Workspace -> Runtime
===================================================================================

[CLI / TUI 启动]
      │
      v
[config/__init__.py] -------> 合并 .env 与 .pico.toml 配置
      │
      v
[core/workspace.py] --------> 探测 Git 仓库跟路径、加载 .gitignore 与白名单
      │
      v
[providers/runtime.py] -----> 校验 Provider 密钥，实例化 ModelClient
      │
      v
[core/runtime.py: Pico.create()] ---> 组装全量依赖，完成 Runtime 实例化


===================================================================================
2. 执行线 (Execution Line): Task -> Context -> Step Loop -> Final Readiness -> Store
===================================================================================

[用户提交指令: runtime.ask()]
      │
      v
[core/context_orchestrator.py] ----> 评估 Context Pressure，组装 Prompt & Sections
      │
      v
[core/engine.py: AgentEngine.run()] <-------------+  (Step 迭代循环)
      │                                            │
      ├──> [providers/clients.py] 求解 LLM API       │
      │                                            │
      ├──> [已判定输出 <final>]:                   │
      │     └── [core/final_readiness.py] 审计就绪   │
      │          ├── 验证通过 -> 返回 Final Answer │
      │          └── 验证未通过 -> 阻断退出并打回 ──┤
      │                                            │
      └──> [已判定工具调用 <tool>]:                │
            └── [core/tool_executor.py] 执行网关   │
                 ├── [features/sandbox] 沙箱防护   │
                 └── 写入历史 ----------------------┘
      │
      v
[features/memory_quarantine.py] ---> 记忆检疫池过滤与格式 Lint 校验
      │
      v
[.pico/ 审计持久化] -----------------> 刷入 session.json、trace.jsonl 与 report.json
```

## 5. `runtime.ask()` 运行时的 10 阶段完整生命周期

当外部调用 `runtime.ask(user_message)` 时，内部按以下 10 个阶段精准推进：

```text
阶段 1: 创设 TaskState
  └── 生成全局唯一的 run_id，初始化 Step 步数预算 (step_budget=30) 与尝试计数器 (attempts)。

阶段 2: 刷新 System Prefix 指纹
  └── 检查 Git HEAD SHA、工作区指纹，计算 prefix_hash 并匹配 Prompt Caching。

阶段 3: 评估 Checkpoint 恢复与代码漂移
  └── 校验会话关联的上次提交；若文件发生外部变更，标记物理路径为 stale_paths。

阶段 4: 上下文编排 (Context Orchestrator)
  └── 分组计算 System, Workspace, Memory, History 各 Section 的 Token 占比与 Context Pressure。

阶段 5: Token 超预算自适应压缩
  └── 若 Context Pressure 超阈值且 History > 4 轮，触发 compact_history() 生成 compact_summary。

阶段 6: 启动 ReAct Step 迭代循环
  └── 进入 AgentEngine.run() 循环，调用 ModelClient 请求 LLM API。

阶段 7: 工具执行网关与安全校验
  └── 模型返回 <tool> 时，ToolExecutor 进行 ToolProfile 过滤、Repeated Tool 拦截与 Read Freshness 校验。

阶段 8: 完成治理就绪检查 (Final Readiness)
  └── 模型返回 <final> 时，FinalReadiness 校验是否修改过代码但未跑测试。未通过则强行打回并要求验证。

阶段 9: 记忆抽取与检疫池过滤
  └── 提取回答中的 <memory> 标签，送入 MemoryQuarantine 校验。通过者写入 Daily Log，冲突者进隔离池。

阶段 10: 持久化落地与清场
  └── 刷入 .pico/sessions/<session_id>.json 与 .pico/runs/<run_id>/trace.jsonl 和 report.json。
```

## 6. 持久化目录与工件规范

Pico v3 在工作区根目录下统一维护 `.pico/` 隐藏审计目录：

- **`.pico/sessions/<session_id>.json`**：会话全量状态镜像（包含历史消息、`compact_summary`、`working` 记忆、`todos` 账本）。
- **`.pico/runs/<run_id>/trace.jsonl`**：按时间轴追加的单次运行原子事件日志（用于调试与 `FakeModelClient` 回放）。
- **`.pico/runs/<run_id>/report.json`**：单次运行的性能报告（包含 `tool_steps`、`context_usage`、`stop_reason`）。
- **`.pico/memory/`**：长期分层记忆存储（包含 `MEMORY.md`、`topics/*.md`、`logs/*.md` 与 `quarantine/`）。
