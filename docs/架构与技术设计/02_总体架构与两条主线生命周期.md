# Chapter 2: 总体架构与两条主线生命周期

在 Chapter 1 中，我们明确了 Pico 选择轻量自研 Harness 的设计哲学与三大 ADR。本章我们将深入 Pico 的内部视角，解构系统的整体架构、**两条核心主线（装配线与执行线）**以及单次任务运行时的 **10 阶段完整生命周期**。

---

## 2.1 总体架构与模块职责图谱

Pico 源码采用模块化分层设计，划分为 `core` 核心调度层、`features` 扩展能力层与 `providers` 模型对接层：

```text
pico/
├── core/
│   ├── runtime.py               # Runtime 门面类: 控制生命周期、密匙脱敏、事件广播
│   ├── engine.py                # AgentEngine 主循环调度器: 驱动 ReAct 感知-决策-行动-验证
│   ├── context_orchestrator.py  # ContextOrchestrator 上下文编排与 Sections 留存
│   ├── context_pressure.py      # ContextPressure 动态计算 Token 占用与压力百分比
│   ├── final_readiness.py       # FinalReadiness 最终回答就绪检查硬性门禁
│   ├── completion_governance.py # CompletionGovernance 判定代码编译与测试验证通过状态
│   ├── vision.py                # Vision 多模态图像与媒体上下文解析
│   ├── model_router.py          # ModelRouter 动态模型路由与降级策略
│   ├── worker_manager.py        # WorkerManager Worker 子 Agent 派发与 write_scope 隔离
│   ├── plan_mode.py             # PlanModeController Plan 模式控制与 implementation_plan 生成
│   ├── todo_ledger.py           # TodoLedger Task 拆解与待办清单流转
│   ├── tool_executor.py         # ToolExecutor 工具网关: 8 重安全校验与快照比对
│   ├── tool_profiles.py         # ToolProfile 动态工具面过滤 (default/plan/readonly/dream)
│   ├── permissions.py           # PermissionChecker 风险审批策略与安全拦截
│   ├── runtime_checkpoints.py   # Checkpoint 创建、代码漂移评估与身份解绑
│   ├── session_store.py         # SessionStore 读写 .pico/sessions/*.json
│   └── run_store.py            # RunStore 写入 .pico/runs/<run_id>/ (trace/report)
└── features/
    ├── memory.py                # LayeredMemory 门面、工作记忆、打分召回与 Auto-Dream
    ├── memory_quarantine.py     # MemoryQuarantine 记忆检疫池: 隔离未知坏数据
    ├── memory_lint.py           # MemoryLint 记忆格式合法性与冲突校验器
    └── sandbox/                 # Shell 命令安全隔离防护沙箱
```

## 2.2 两条主线运作流程 (Setup Line & Execution Line)

Pico 的运作分为**装配线**（初始化环境与依赖）与**执行线**（单次 ReAct 循环驱动与治理）：

```text
===================================================================================
1. 装配线 (Setup Line): CLI -> Config -> Workspace -> Runtime
===================================================================================

[CLI / TUI 启动 (pico/cli.py)]
      │
      v
[config/__init__.py] -------> 合并 .env 与 .pico.toml 配置
      │
      v
[core/workspace.py] --------> 探测 Git 仓库跟路径、加载 .gitignore 与白名单
      │
      v
[providers/runtime.py] -----> 校验 Provider 密钥，实例化 ModelClient
      │
      v
[core/runtime.py: Pico.create()] ---> 组装全量依赖，完成 Runtime 实例化


===================================================================================
2. 执行线 (Execution Line): Task -> Context -> Step Loop -> Final Readiness -> Store
===================================================================================

[用户提交指令: runtime.ask(user_message)]
      │
      v
[core/context_orchestrator.py] ----> 评估 Context Pressure，组装 Prompt & Sections
      │
      v
[core/engine.py: AgentEngine.run()] <-------------+  (Step 迭代循环)
      │                                            │
      ├──> [providers/clients.py] 求解 LLM API       │
      │                                            │
      ├──> [已判定输出 <final>]:                   │
      │     └── [core/final_readiness.py] 审计就绪   │
      │          ├── 验证通过 -> 返回 Final Answer │
      │          └── 验证未通过 -> 阻断退出并打回 ──┤
      │                                            │
      └──> [已判定工具调用 <tool>]:                │
            └── [core/tool_executor.py] 执行网关   │
                 ├── [features/sandbox] 沙箱防护   │
                 └── 写入历史 ----------------------┘
      │
      v
[features/memory_quarantine.py] ---> 记忆检疫池过滤与格式 Lint 校验
      │
      v
[.pico/ 审计持久化] -----------------> 刷入 session.json、trace.jsonl 与 report.json
```

## 2.3 `runtime.ask()` 10 阶段运行生命周期

当外部调用 `runtime.ask(user_message)` 时，底层精确流转以下 10 个阶段：

```text
阶段 1: 创设 TaskState
  ├── 在 pico/core/runtime.py 中实例化 TaskState 对象。
  └── 生成全局唯一的 run_id，初始化 Step 步数预算 (step_budget=30) 与尝试计数器 (attempts)。

阶段 2: 刷新 System Prefix 指纹
  ├── 检查 Git HEAD SHA、工作区指纹 (workspace.fingerprint())。
  └── 计算 prefix_hash 并匹配 Prompt Caching。

阶段 3: 评估 Checkpoint 恢复与代码漂移
  ├── 校验会话关联的上次 Git Commit SHA。
  └── 若物理文件发生外部变更，标记物理路径为 stale_paths。

阶段 4: 上下文编排 (ContextOrchestrator)
  ├── 捕获 ContextSnapshot 快照。
  └── 分组计算 System, Workspace, Memory, History 各 Section 的 Token 占比与 Context Pressure。

阶段 5: Token 超预算自适应压缩
  └── 若 pressure_tier == "tier3_summary" 且 History > 4 轮，触发 compact_history() 生成 compact_summary。

阶段 6: 启动 ReAct Step 迭代循环
  ├── 进入 AgentEngine.run() 循环。
  └── 调用 ModelClient 请求 LLM API，解析返回文本中的 <tool> 或 <final>。

阶段 7: 工具执行网关与安全校验
  ├── 模型返回 <tool> 时，进入 run_tool() 网关。
  └── 依次执行 ToolProfile 过滤、Repeated Tool 拦截、Read Freshness 校验及快照比对。

阶段 8: 完成治理就绪检查 (Final Readiness)
  ├── 模型返回 <final> 时，FinalReadiness 校验是否修改过代码但未跑测试。
  └── 未通过时 (action=="block") 强行打回并注入提示语要求继续验证。

阶段 9: 记忆抽取与检疫池过滤
  ├── 提取回答中的 <memory> 标签卡片。
  └── 送入 MemoryQuarantine 与 MemoryLint 校验。通过者写入 Daily Log，冲突者进 quarantine/ 隔离池。

阶段 10: 持久化落地与清场
  └── 刷入 .pico/sessions/<session_id>.json 与 .pico/runs/<run_id>/trace.jsonl 和 report.json。
```
