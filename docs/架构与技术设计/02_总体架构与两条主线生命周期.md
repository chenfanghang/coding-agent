# Chapter 2：总体架构与两条主线生命周期

> [上一章：设计哲学与架构选型](<./01_设计哲学与架构选型(ADR).md>) · [下一章：受控工具网关与安全质量门禁](./03_受控工具网关与安全质量门禁.md)

> **本章关注**：Runtime 如何装配，单次请求如何在 Context、Engine、Tool、Recovery 与 Store 之间流转，以及不同状态工件各自负责什么。

---

## 2.1 核心分层

```text
CLI / TUI
   |
   v
Runtime 门面与会话状态
   |
   +--> Context：前缀、记忆、历史、当前请求
   +--> Engine：模型调用、输出解析、步骤预算
   +--> Tools：Schema、权限、策略、执行证据
   +--> Recovery：Checkpoint、Freshness、Runtime Identity
   +--> Collaboration：Plan Mode、Todo、Worker
   |
   v
Provider Client + Workspace + .pico/ 持久化
```

主要模块职责如下：

| 层次 | 模块 | 职责 |
| :--- | :--- | :--- |
| 运行时 | `pico/core/runtime.py` | 装配依赖，维护会话、工具、记忆与事件总线 |
| 调度 | `pico/core/engine.py` | 驱动模型调用、工具步骤和最终答复判断 |
| 上下文 | `context_orchestrator.py`、`context_manager.py` | 构建 Prompt、计算压力并触发历史压缩 |
| 工具治理 | `tool_executor.py`、`permissions.py`、`tool_policy.py` | 校验、授权、执行工具并记录副作用 |
| 状态 | `runtime_checkpoints.py`、`task_state.py` | 保存可恢复任务状态并识别陈旧或不一致环境 |
| 协同 | `plan_mode.py`、`todo_ledger.py`、`worker_manager.py` | 约束规划模式、维护待办和管理子 Agent |
| 持久化 | `session_store.py`、`run_store.py` | 分离可恢复会话状态与单次运行审计工件 |

### 依赖方向

```text
CLI / TUI
   -> Runtime Facade
      -> Core Services
         -> Provider / Tools / Features
            -> Workspace & File Stores
```

上层负责组合与交互，下层负责能力与持久化。Provider 不应反向决定任务是否完成，Tool Runner 也不应绕过 Runtime 直接修改会话控制状态。

## 2.2 两条主线

### 装配线（Setup Line）

```text
读取配置
  -> 发现 Workspace
  -> 创建 Provider Client
  -> 加载 Session / Memory / Skills
  -> 注册 Tool Profile
  -> 组装 Runtime
```

装配线只负责建立一次运行所需的依赖和边界。Provider、工具配置或工作区发生变化时，Runtime 会刷新相关身份与前缀状态。

### 执行线（Execution Line）

```text
用户请求
  -> 创建 TaskState 与 Run 工件
  -> 检查恢复状态和工作区新鲜度
  -> 编排上下文
  -> 调用模型并解析输出
       |-- 工具调用 -> 受控执行 -> 更新状态 -> 继续下一步
       `-- 最终答复 -> Final Readiness -> 放行、提醒或阻断
  -> 保存 Session、TaskState、Trace 与 Report
```

这是一条概念执行链路，不是源码中的固定“十状态枚举”。某些阶段会因运行模式、是否存在 Checkpoint、模型是否调用工具而跳过或重复。

## 2.3 状态与工件边界

- **Session**：保存跨轮次对话、Todo、Worker 和运行模式等可续接状态。
- **TaskState**：保存单次请求的目标、步骤、工具证据、验证证据和停止原因。
- **Trace**：按发生顺序追加结构化事件，用于解释一次运行做了什么。
- **Report**：面向评测或审计的汇总结果。
- **Artifacts**：保存不适合长期内联到 Prompt 的大型工具输出。

把恢复状态与审计工件分开，可以避免为了调试 Trace 而污染会话，也避免仅靠聊天历史猜测任务进度。

## 2.4 任务恢复链路

恢复不是“把旧聊天重新放回 Prompt”，而是判断旧任务状态在当前环境中是否仍可信。

```text
发现 Checkpoint
      |
      v
检查 Schema 与任务字段完整性
      |
      v
比较 Runtime Identity
  Provider / Model / Tool Signature / Workspace
      |
      v
检查关键文件 Freshness
      |
      +--> 完全一致：恢复 Goal、Next Step、Todo 与 Evidence
      |
      +--> 文件陈旧：使相关摘要失效，要求重新读取和重锚定
      |
      `--> 身份不一致：拒绝直接续跑，暴露 mismatch 字段
```

这种设计选择“安全暴露不一致”，而不是为了提高恢复率猜测旧状态。详细实验见 [任务恢复评测](../评测体系/06_任务恢复评测.md)。

## 2.5 一次请求中最重要的控制边界

| 边界 | 模型可以决定 | Harness 必须决定 |
| :--- | :--- | :--- |
| 下一步动作 | 建议调用哪个工具及参数 | 工具是否存在、是否授权、是否满足策略 |
| 上下文 | 利用提供的信息进行推理 | 哪些区块进入 Prompt、何时压缩、保留什么 |
| 任务进度 | 提议 Todo 状态或下一步 | 状态如何持久化、能否安全恢复 |
| 最终交付 | 生成用户可读答案 | 证据是否满足 Final Readiness |
| 子任务 | 提议派发 Worker | Worker 类型、生命周期和写入作用域 |

## 2.6 Turn 状态转换与终止语义

模型调用只是 Turn 的一个环节。Engine 还需要处理 Provider 重试、输出解析失败、步骤预算、用户终止和完成门禁。

```text
Build Prompt
     |
     v
Model Request
     |
     +--> Provider Error --可重试--> Provider Retry --------+
     |                  `--不可重试--> Model Error + Checkpoint
     |
     +--> Parse Error ----------------> Parse Retry / Retry Limit
     |
     +--> Tool Batch -----------------> Execute -> Continue --+
     |
     +--> Plan / Readiness Notice ----> Continue -------------+
     |
     `--> Final Answer ---------------> Finish

外部 Abort --------------------------> Aborted
Step Budget Exhausted ---------------> Step Limit + Summary
Strict Final Gate Hard Reason -------> Final Gate Blocked
```

主要继续原因包括 `provider_retry`、`parse_retry`、`tool_batch_executed`、`plan_notice` 和 `final_readiness_notice`；主要终止原因包括 `final_answer_returned`、`aborted`、`model_error`、`step_limit_reached`、`retry_limit_reached` 与 `final_gate_blocked`。

模型错误会记录 Provider 错误元数据、写入 TaskState、创建 Checkpoint 并生成终止事件。这样基础设施错误不会被误记为 Agent 已正常完成。

## 2.7 示例：一次 Bugfix 请求如何流转

假设用户请求：“修复登录超时问题并运行相关测试。”

| 阶段 | Pico 的动作 | 产生的关键状态 |
| :--- | :--- | :--- |
| 接收请求 | 创建 TaskState 和 Run 目录 | `run_id`、`task_id`、`user_request` |
| 恢复判断 | 检查旧 Checkpoint、Runtime Identity 和关键文件 Freshness | `resume_status`、`stale_paths` |
| 上下文构建 | 组装稳定前缀、Memory、Skill、History 和 Current Request | `prompt_metadata`、`pressure_tier` |
| 模型决策 | 模型提出搜索或读取登录相关代码 | `model_requested`、解析结果 |
| 工具治理 | 校验参数、权限与策略，读取目标文件 | Permission / Policy / Tool Evidence |
| 修改代码 | Fresh Read 通过后执行 Patch，记录前后 Workspace 差异 | `affected_paths`、`diff_summary` |
| 执行验证 | 运行目标测试并记录退出状态 | Verification Evidence |
| 完成判断 | Final Readiness 检查未完成项、验证与必需工件 | `allow` / `warn` / `block` |
| 结果落盘 | 保存 TaskState、Trace、Report 与大型输出 | `.pico/runs/<run_id>/` |

这个例子展示了 Pico 的核心边界：模型决定“下一步想做什么”，Runtime 决定“能不能做、结果是什么、是否足以结束”。

## 2.8 模型路由与能力选择

`ModelClientRouter` 默认使用主模型；当输入包含图片时，可以按需创建或选择 Vision Client。模型路由只负责选择能力匹配的 Client，不负责判断任务完成，也不绕过统一的错误、Usage 和 Trace 链路。

当前路由保持简单：文本请求走 Main Client，包含图像的输入走 Vision Client；如果未配置独立 Vision Client，则回退到主模型。未来增加快慢模型或成本路由时，应继续保持“路由负责选模型，Engine 负责控制流程”的边界。

## 2.9 本章小结

Pico 的核心并不是某个单独算法，而是把上下文、工具、任务状态、恢复和审计接入同一条运行链路。后续章节会分别展开这些控制面，但它们最终都通过 Runtime、TaskState 和事件工件汇合。

### 面试表达

> **30 秒讲法**：一次请求先由 Runtime 装配 Provider、Workspace、Memory、Skill 和工具配置，再进入 Engine 控制循环。每轮会经历恢复判断、上下文构建、模型决策、工具治理、状态更新和完成判断；失败、重试与预算耗尽都有明确停止原因，最终状态会进入 Run 工件。

**项目推演题（非真实面经）**：Turn、Run 和单次模型调用有什么区别？模型请求工具后 Runtime 如何继续？Provider 失败、解析失败和工具失败分别如何处理？为什么控制逻辑放在模型外？

**回答边界**：回答时沿一条真实任务链路展开，不要只背模块名称；同时区分 Session 级状态与单次 Run 的审计状态。
