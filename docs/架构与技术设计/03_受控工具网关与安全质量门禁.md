## 3.1 设计原则：模型意图与权限分离

大模型输出的仅为“动作建议”，绝不应直接等同于系统的操作系统权限。Pico 将工具治理放在模型之外，核心原则是：**模型提出工具意图，Harness 网关负责校验、鉴权、防重、拦截与副作用审计**。

### 3.1.1 信任边界矩阵

| 参与者 | 默认信任程度 | Pico 的处理方式 |
| :--- | :--- | :--- |
| **用户请求** | 任务目标可信，具体输入仍需校验 | 保留当前请求，但不直接转化为操作系统 Shell 命令。 |
| **大模型输出** | 不可信动作建议 | 必须强行经过 8 重受控关卡（Schema、Permission、Policy 等）。 |
| **Provider 响应** | 可用但可能超时、为空或格式异常 | 统一错误分类、有限重试与终止状态记录。 |
| **Workspace 文件** | 当前物理状态可信，旧摘要可能陈旧 | 路径逃逸约束 (`path_escape`)、Freshness 动态比对与快照 Diff。 |
| **Tool Runner** | 受控能力实现，但仍可能部分失败 | 执行前后采集状态并记录 `partial_success`。 |
| **Memory 候选** | 可能陈旧、含 Secret 或注入指令 | 经过 `MemoryLint`、`Status`、`Evidence` 与 `Quarantine` 隔离。 |

> *注：Pico 的 Tool Policy 属于应用层 Harness 治理。若需执行完全不可信的二进制或对抗性代码，系统支持外挂独立 Sandbox。*

## 3.2 8 重受控工具网关执行链条 (`run_tool`)

在源码 `pico/core/tool_executor.py` 的 `run_tool()` 中，每一次工具调用请求必须依次通过以下 **8 重受控关卡**：

```text
Model Intent: tool_name(args)
          │
          ▼
┌────────────────────────────────────────────────────────┐
│ 关卡 1: Tool Lookup (检查工具是否在注册表中)            │
├────────────────────────────────────────────────────────┤
│ 关卡 2: Schema & Path Escape (校验参数与沙箱路径越权)   │
├────────────────────────────────────────────────────────┤
│ 关卡 3: Repetition Check (相同参数重复调用打断防死循环)│
├────────────────────────────────────────────────────────┤
│ 关卡 4: Permission Check (只读模式与 write_scope 检查)   │
├────────────────────────────────────────────────────────┤
│ 关卡 5: Tool Policy (Read Freshness 读后修改策略检查)   │
├────────────────────────────────────────────────────────┤
│ 关卡 6: Approval Policy (高危动作人工/自动审批)          │
├────────────────────────────────────────────────────────┤
│ 关卡 7: Side-effect Log (统一治理决策日志审计)         │
├────────────────────────────────────────────────────────┤
│ 关卡 8: Artifact Offloading (超长结果磁盘工件化)        │
└─────────────────────────┬──────────────────────────────┘
                          ▼
                   Execute Tool (安全落盘)
```

## 3.3 核心受控防护策略

### 3.3.1 Read Freshness Guard（读后修改保护）
* **解决痛点**：防止大模型凭空想象代码内容并强行覆写磁盘文件（覆写乱抹风险）。
* **实现机制**：当模型尝试执行 `write_file`、`patch_file` 或 `replace_file_content` 时，网关检查该路径在当前 Session 中是否已被 `view_file` 或 `read_file` 访问过。若未读过，网关直接阻断并提示：*“Please use view_file to inspect the file content before making edits.”*
* **效果**：盲目覆写拦截率 **100%**。

### 3.3.2 路径逃逸防护与沙箱隔离 (`canonicalize_path`)
* **解决痛点**：防止模型通过 `../../../../etc/passwd` 等路径绕过 Working Directory。
* **实现机制**：利用 `resolve_workspace_path()` 强制转换为规范绝对路径，并执行 `path.relative_to(workspace_root)` 校验。一旦越权，触发关卡 2 拦截，返回 `security_event_type: "path_escape"`。

### 3.3.3 重复调用死循环阻断 (`repeated_tool_call`)
* **解决痛点**：防范 Agent 在面对无法修复的错误时，连续 10 轮用完全相同的参数反复调用同一工具。
* **实现机制**：检测上一轮工具调用的名称与参数。若连续两次完全一致，网关强制拒绝并要求：*“choose a different tool or return a final answer”*。

## 3.4 治理决策审计日志 (`record_governance_decision`)

每一次拦截或放行，均会记录统一的结构化治理日志：

```json
{
  "event": "governance_decision",
  "tool_name": "replace_file_content",
  "decision": "deny",
  "reason_code": "read_freshness_required",
  "decision_type": "tool_policy",
  "security_event_type": "unread_modify_block"
}
```
