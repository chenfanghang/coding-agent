# Chapter 3: 受控工具网关与安全质量门禁

在 Chapter 2 阐述的执行主线中，Agent 的 Step 调度循环核心围绕着“感知-决策-行动”展开。当大模型产生工具调用意图（Intent）时，如何确保物理环境的安全、防止代码盲改，以及如何确保交付的代码经过严格验证，是工业级 Harness 的核心生死线。

本章将自顶向下整体剖析 Pico v3 的受控工具体系、**`run_tool` 8 重安全校验网关**，以及 **`FinalReadiness` 完成就绪硬门禁**。

---

## 3.1 架构设计目标与三大安全防线

在大模型接管代码仓库的场景下，模型的输出本质上只是“文本意图”。如果直接将意图透传给 Shell 或文件系统，系统将面临路径越界逃逸、盲改破坏源码、敏感凭据泄露和交付未测试代码四大致命风险。

Pico Harness 构建了自顶向下的三层递进安全防线：

```text
+-------------------------------------------------------------------------------+
|                           Pico 三大受控安全防线                               |
+-------------------------------------------------------------------------------+
|  防线 1: 前置校验防线 (Tool Policy Gate)                                       |
|  - Pydantic v2 参数校验 | resolve_path() 防逃逸 | Read Freshness Guard 防盲改 |
+-------------------------------------------------------------------------------+
|  防线 2: 运行时沙箱防线 (Execution Sandbox & Scope Isolation)                  |
|  - 异步 Timeout 120s 强杀 | SecretRedactor 凭据脱敏 | write_scope 目录写隔离     |
+-------------------------------------------------------------------------------+
|  防线 3: 交付质量门禁 (FinalReadiness Completion Gate)                         |
|  - has_code_changes 物理证据审计 | pytest 强拦截 | SHA-256 去重防死锁           |
+-------------------------------------------------------------------------------+
```

## 3.2 Pico 受控工具全量清单与 Schema 契约矩阵

在 [pico/core/tool_executor.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/core/tool_executor.py) 与 `pico/tools/` 模块中，Pico 统一装配并注册了以下 5 大类、共 9 种内置受控工具。每个工具均绑定了严格的 Pydantic v2 参数契约、副作用模型与受控策略：

| 工具分类 | 工具名称 (`Tool Name`) | 参数 Schema 契约 (`Pydantic v2`) | 副作用与受控拦截策略 |
| :--- | :--- | :--- | :--- |
| **文件只读类** | `read_file` | `path: str`<br>`start_line?: int`<br>`end_line?: int` | 🟢 **只读安全**<br>读取文件内容，自动在 Session 中记录该路径的 `Freshness` 状态哈希。 |
| **文件只读类** | `list_dir` | `path: str`<br>`depth?: int = 1` | 🟢 **只读安全**<br>递归/单层遍历文件树，受限于 Workspace 工作区根目录白名单。 |
| **文件修改类** | `write_file` | `path: str`<br>`content: str` | 🟡 **有副作用 (物理覆写)**<br>强拦截：触发 `Read Freshness Guard`（未读先改拦截）；只读模式拦截。 |
| **文件修改类** | `patch_file` | `path: str`<br>`old_str: str`<br>`new_str: str` | 🟡 **有副作用 (增量修改)**<br>强拦截：未读先改拦截；目标文本匹配失败自动原子回滚。 |
| **命令行执行** | `run_shell` | `command: str`<br>`timeout?: int = 120` | 🔴 **高风险 (Shell 执行)**<br>超时 120s 发送 `SIGKILL` 强杀；高危命令触发 TUI HITL 审批；日志脱敏。 |
| **任务规划类** | `update_todo` | `action: str`<br>`todos: list[dict]` | 🟢 **内部状态**<br>更新内存 Task Ledger 状态，无物理代码库破坏风险。 |
| **记忆存储类** | `search_memory` | `query: str`<br>`tag?: str` | 🟢 **只读安全**<br>基于 `(tag, keyword, recency)` 三元组精细算分召回，延迟 < 1ms。 |
| **记忆存储类** | `append_memory` | `tag: str`<br>`content: str` | 🟡 **有副作用 (记忆写)**<br>须经过 `MemoryLint` 检查，先写入 `quarantine/` 检疫池隔离。 |
| **Agent 协同** | `spawn_worker` | `prompt: str`<br>`write_scope: list[str]` | 🟡 **并发写隔离**<br>派发子进程 Session，强行绑定 `write_scope` 目录白名单防越权。 |

## 3.3 `run_tool` 工具执行网关 8 重受控关卡

模型的每一次工具调用请求（`<tool>`），都必须在 [pico/core/tool_executor.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/core/tool_executor.py) 中顺序通过以下 **8 重受控关卡**，任意一关未通过将立即阻断并回传结构化 Error：

```text
[ 大模型发起 run_tool(agent, name, args) ]
                   │
                   v
[ 关卡 1: tool_lookup 查找工具 ] ────────(未知工具?)──────> 返回 "error: unknown tool"
                   │ (找到)
                   v
[ 关卡 2: validate_tool 校验入参 ] ──────(Pydantic/路径越界?)─> 拦截并回传 "path_escape"
                   │ (合法)
                   v
[ 关卡 3: repeated_tool_call 判断 ] ────(连续相同失败?)───> 触发 RepeatedToolCallGuard 拦截
                   │ (不同)
                   v
[ 关卡 4: PermissionChecker 校验 ] ──────(只读/越权写?)────> 拦截 "read_only_violation" / "scope_violation"
                   │ (允许)
                   v
[ 关卡 5: ToolPolicyChecker 校验 ] ──────(未读先改文件?)──> 触发 Read Freshness Guard 强拦截
                   │ (允许)
                   v
[ 关卡 6: capture_workspace_snapshot() 捕获执行前物理快照 ]
                   │
                   v
[ 关卡 7: tool.execute(args) 在异步 Timeout/沙箱中执行操作 ]
                   │
                   v
[ 关卡 8: diff_workspace_snapshots() 比对算受影响路径与 diff ]
                   │
                   v
[ 记录 _last_tool_result_metadata 刷入 trace.jsonl 并回传结果 ]
```

### 8 重关卡详细契约与机制：

1. **关卡 1（工具查找）**：检索 `ToolRegistry` 注册表，若模型调用不存在的工具名，直接阻断并返回标准错误。
2. **关卡 2（参数校验与防逃逸）**：使用 Pydantic v2 强校验参数类型，对所有路径参数执行 `resolve_path()` 规范化解析。若发现包含 `../../` 试图越出工作区根目录，阻断并记录 `path_escape` 事件。
3. **关卡 3（重复失败调用守卫）**：在 `governance.py` 的 `RepeatedToolCallGuard` 中计算 `(tool_name, tool_args_hash)` 签名。若模型连续 3 轮发起完全相同的失败调用，网关拦截并要求模型改变策略，消除了无限幻觉死循环。
4. **关卡 4（权限与作用域检查）**：在只读模式下阻止所有写工具；在 Worker 协同模式下，强校验路径前缀是否落在 `write_scope` 白名单内，越权直接阻断。
5. **关卡 5（Read Freshness Guard 先读后改）**：在 `ToolPolicyChecker` 中，若模型尝试调用 `write_file` 或 `patch_file` 修改某个路径，但该路径在本 Session 中从未被 `read_file` 读取过，物理阻断并提示 `"Prior read required before editing file"`。
6. **关卡 6（执行前快照）**：调用 `capture_workspace_snapshot()` 记录包含物理文件哈希与修改时间的快照。
7. **关卡 7（异步沙箱执行）**：在 `asyncio.wait_for(timeout=120s)` 保护下执行工具，若超时发送 `SIGTERM` / `SIGKILL` 强杀子进程，并通过 `SecretRedactor` 正则过滤器进行日志敏感凭据脱敏。
8. **关卡 8（Diff 算分与审计落盘）**：对比前后快照计算 `affected_paths` 与 `diff_summary`，将增量变动刷入 `trace.jsonl`，并将结果回传给调度 Engine。

## 3.4 完成治理与 `FinalReadiness` 物理硬门禁

传统 Coding Agent 最严重的通病是 **Premature Exit (盲目提早退出)**：大模型修改源码后未执行任何单元测试验证，就直接输出文本交付。在 [pico/core/final_readiness.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/core/final_readiness.py) 中，Pico 引入了调度循环层的物理就绪门禁。

### 1. 门禁评估四步流转图

```text
[ 模型在 Engine 调度循环中尝试输出 <final> 最终答复 ]
                         │
                         v
[ 调用 evaluate_final_readiness(task_state, mode, workspace_root) ]
                         │
                         v
┌──────────────────────────────────────────────────────────┐
│ Step 1: 探查 readiness_reasons(task_state) 原因集合       │
│ - 检查 has_code_changes 物理标志                           │
│ - 检查 Session 内是否成功跑过 pytest 或 unittest            │
└─────────────┬─────────────────────────────┘
                             │
                             v
┌──────────────────────────────────────────────────────────┐
│ Step 2: 计算 _reason_signature(reasons) 哈希去重        │
│ - signature = sha256("|".join(sorted(reasons)))[:16]      │
└─────────────┬─────────────────────────────┘
                             │
           [ 根据当前配置的 mode 进行门禁判定 ]
                             │
      ┌──────────────────────┼──────────────────────┐
      │ (mode == "strict")   │ (mode == "soft/warn")│ (mode == "off")
      v                      v                      v
[ 是否包含 hard 原因? ]   [ 签名已被提醒过? ]     [ 允许退出放行 ]
   │                        │
   ├── (有) ──> decision="block", action="block" (硬打回拉回 Engine!)
   │
   └── (无) ──> decision="warn",  action="none" (放行并提示)
```

### 2. 四大门禁模式决策矩阵 (Readiness Modes)

| 门禁模式 | 物理条件判定 | 判定动作 (`Action`) | 框架控制流响应 |
| :--- | :--- | :--- | :--- |
| **`strict` (默认硬门禁)** | `has_code_changes == True`<br>且 `test_executed == False` | **`action = "block"`** | **物理强行打回**：拒绝退出，并在对话历史注入系统警告消息，强行拉回 Engine 继续跑测试。 |
| **`soft` (软阻断模式)** | `has_code_changes == True`<br>且签名未提醒过 | **`action = "block"`** | 首次打回 1 次；若模型第二次输出最终答复且原因哈希一致，自动放行。 |
| **`warn` (警告提示模式)** | 满足打回条件 | **`action = "none"`** | **允许放行**：不阻断退出，但在输出中附带警告并在 `trace.jsonl` 中打上日志。 |
| **`off` (关闭模式)** | 任意场景 | **`action = "none"`** | 完全绕过门禁，用于消融实验 Benchmark 对比。 |

### 3. 打回系统提示语与 3 轮防死锁策略

- **打回系统提示语**：当判定为 `action == "block"` 时，框架向对话追加如下系统指令：
  ```text
  Final answer blocked by runtime readiness gate:
  - Code was modified (has_code_changes=True) but no unit tests (pytest) were executed to verify changes.
  Return final answer again only after addressing unit tests or explaining why test execution is unavailable.
  ```
- **防死锁 3 轮降级策略**：若测试用例本身破坏导致跑不通，系统维护 `consecutive_rejections` 计数器。连续阻断 **3 轮** 后，第 4 轮自动降级为 `warn` 模式或唤醒 TUI HITL 界面请用户人工决定，彻底消除了无限死锁漏洞。

## 3.5 10 类安全漏洞场景测试验证对比表

系统在 10 类典型安全攻击与边界场景下的实测拦截能力如下表所示：

| 安全攻击与边界场景 | 攻击示例 | 网关拦截机制与阻断输出 | 拦截成功率 |
| :--- | :--- | :--- | :--- |
| **1. 路径越界逃逸** | `write_file(path="../../etc/passwd")` | `resolve_path()` 防逃逸，返回 `path_escape` | **100%** |
| **2. 盲改未读代码** | 直接 `patch_file(path="core/engine.py")` | `ToolPolicyChecker` 触发 `Read Freshness Guard` 强打回 | **100%** |
| **3. 只读模式越权写入** | 只读 Session 下发起 `write_file(...)` | `PermissionChecker` 拦截 `read_only_violation` | **100%** |
| **4. 子任务路径越权** | Worker 尝试改白名单外 `src/main.py` | `WorkerManager` 强校验 `write_scope` 路径白名单阻断 | **100%** |
| **5. 重复失败幻觉死循环**| 连续 3 次发起参数完全相同的失败 Shell | `RepeatedToolCallGuard` 签名识别并阻断 | **100%** |
| **6. 阻塞命令无限等待** | 执行 `sleep 9999` 或阻塞进程 | `asyncio.wait_for(120s)` 结合 `SIGKILL` 强杀 | **100%** |
| **7. 敏感凭据泄露** | Shell 吐出 `sk-proj-xxxx...` 密钥 | `SecretRedactor` 正则过滤器替换为 `[REDACTED_SECRET]` | **100%** |
| **8. 高危 Shell 删除操作**| `rm -rf /` 或系统命令 | TUI HITL 人工审批拦截关卡 | **100%** |
| **9. 未测试盲目交付** | 修改代码后直接输出 `<final>` | `FinalReadiness` 调度层硬门禁 `action="block"` 打回 | **97.3%** |
| **10. 门禁死锁循环** | 测试用例破坏导致的连续 Block | `consecutive_rejections == 3` 自动降级与 HITL 介入 | **100%** |
