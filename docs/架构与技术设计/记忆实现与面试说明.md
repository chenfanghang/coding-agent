# Pico v3 记忆系统与面试技术说明

本文深度剖析 `pico v3` 记忆系统的架构哲学、四层数据协议、打分召回数学公式、Memory Quarantine (记忆检疫池) 与 Auto-Dream 后台并发机制。

## 1. 为什么放弃 Vector DB / RAG？(第一性原理推导)

在本地 Coding Agent Harness 场景下，业内普遍盲目套用 Vector DB (RAG) 方案。我们在 Pico v3 设计初期对 RAG 进行了第一性原理拆解，发现了四大致命缺陷：

```text
+-----------------------------------------------------------------------------------------+
|                    第一性原理拆解: 为什么 Coding Agent 不能依赖 RAG？                    |
+-----------------------------------------------------------------------------------------+
| 1. 代码精度缺陷  : 向量相似度基于语义距离，对精细变量名 (如 user_id vs user_ids)、正则与 |
|                    配置项无法精准区分，召回相似但错误的干扰代码段。                       |
| 2. 检索延时与开销: 在本地 CLI 中绑定 Chroma/Milvus 增加了 50MB+ 依赖包与 200MB+ 内存占用。   |
| 3. 文件变动失效  : 本地代码文件在编辑过程中频繁变动，重新切片与 Embedding 带来极大 CPU 开销。   |
| 4. 黑盒不可控    : 向量数据库中的 Embedding 向量对开发者是黑盒，无法人为直接修正或删除。       |
+-----------------------------------------------------------------------------------------+
```

`pico v3` 选择基于 **分层 Markdown 文本 + Tag 词条算分召回 + Memory Quarantine 检疫隔离池**，做到了 **零额外依赖、< 1ms 检索延时、人类 100% 可读可控**。

## 2. 四层记忆数据协议 (Four-Layer Memory Protocol)

```text
.pico/memory/
├── MEMORY.md                       # 长期记忆大纲索引 (< 200 行，固定进 Prompt)
├── topics/                         # durable memory (4 类主题 Markdown)
│   ├── user-preferences.md         # 1. 用户角色与协作偏好
│   ├── project-conventions.md      # 2. 仓库约定与命名规范
│   ├── key-decisions.md            # 3. 重大架构决策与理由
│   └── dependency-facts.md         # 4. 关键依赖版本与踩坑记录
├── logs/                           # daily logs (只增不减 append-only)
│   └── YYYY/MM/YYYY-MM-DD.md       # 按天追加的原始观察日志
├── quarantine/                     # [v3] memory_quarantine 隔离池 (存放未校验好的候选记忆)
└── .consolidate-lock               # auto-dream PID 互斥锁与时间戳
```

## 3. 动态相关记忆召回算法 (`retrieval_candidates`)

在组装 Prompt 时，[pico/features/memory.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/features/memory.py) 会基于当前用户输入（`query`）计算最相关的记忆条目 (`relevant_memory`)。

### 3.1 打分元组推导公式

对于任意一个候选记忆笔记 $N$，其关联得分由一个三元组 $S(N)$ 决定：

$$S(N) = \Big( \text{exact\_tag\_match}(Q, N), \, \text{keyword\_overlap}(Q, N), \, \text{recency}(N) \Big)$$

其中：
1. **$\text{exact\_tag\_match}(Q, N)$**：用户查询分词集合 $T(Q)$ 与笔记标签集合 $Tag(N)$ 的交集判定：
   $$\text{exact\_tag\_match}(Q, N) = \begin{cases} 1, & \text{if } T(Q) \cap Tag(N) \neq \emptyset \\ 0, & \text{otherwise} \end{cases}$$
2. **$\text{keyword\_overlap}(Q, N)$**：查询分词与笔记全文本及标题分词的重叠词数量：
   $$\text{keyword\_overlap}(Q, N) = \big| T(Q) \cap \big( Text(N) \cup Title(N) \big) \big|$$
3. **$\text{recency}(N)$**：解析 ISO 格式时间戳转为 Unix 秒数，确保新鲜度。

### 3.2 排序与过滤

根据 Python 元组默认按元素顺位降序比较的特性，系统执行：
$$\text{Ranked} = \text{Sort}\Big( \{ S(N) \mid S(N)[0] > 0 \lor S(N)[1] > 0 \} \Big)_{\text{descending}}$$
截取前 3 条 ($\text{limit}=3$) 拼接到 Prompt 的 `Relevant Durable Memories` 段落中。

## 5. 后台 Auto-Dream 梦境炼化与 PID 互斥锁

`auto-dream` 后台守护线程定期将 Daily Logs 与 Quarantine 隔离池中的记录归纳炼化为 Durable Topics：

### 5.1 启动门禁 (`evaluate_auto_dream_gate`)
- 距离上次炼化时间 $\Delta t \ge 24 \text{ 小时}$。
- 自上次炼化以来累积的会话数量 $N_{\text{session}} \ge 5$。

### 5.2 基于 PID 的分布式互斥锁解死锁机制

为了防止主进程与后台 Dream 线程并发修改 `MEMORY.md` 引起物理文件损坏，系统在 `.pico/memory/.consolidate-lock` 上实现了 PID 锁：

```python
def acquire_lock(memory_dir):
    lock_path = memory_dir / ".consolidate-lock"
    current_pid = os.getpid()
    if lock_path.exists():
        stat = lock_path.stat()
        age = time.time() - stat.st_mtime
        holder_pid = int(lock_path.read_text().strip())
        if age < HOLDER_STALE_S:  # 若锁未超时 (如 < 300s)
            try:
                os.kill(holder_pid, 0)  # 探测持锁进程是否仍然在存活
                return False            # 锁有效且被持有着，抢锁失败
            except OSError:
                pass                    # 持锁进程已崩溃，允许清理坏锁
    lock_path.write_text(str(current_pid))
    return True
```
