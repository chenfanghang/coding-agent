# Pico v3 评测与消融体系说明

本文说明 `pico v3` 自动化评测体系的设计原理、`FakeModelClient` 确定性回放机制、HarnessBench 基准测试集以及 3 大消融实验。

---

## 1. 评测的核心目标与设计哲学

在评估 Coding Agent Harness 框架时，最大的挑战在于**模型生成的随机性与波动性**。

为了客观衡量 Pico 框架在状态恢复、工具拦截、安全隔离与上下文治理方面的能力，`pico v3` 的评测体系遵循以下原则：

- **解耦 Harness 框架与 LLM 模型随机性**：使用确定性 Mock/Replay (`FakeModelClient`)，隔离模型生成波动的干扰。
- **引入 HarnessBench 标准测试集**：基于 [pico/evaluation/harnessbench.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/evaluation/harnessbench.py) 覆盖长 Session、多文件重构与依赖升级等多维度真实场景。
- **精确衡量 Context Cost**：基于 [pico/evaluation/context_cost.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/evaluation/context_cost.py) 评估前缀缓存命中率、Token 开销与步骤效益。

## 2. 确定性回放机制 (`FakeModelClient`)

在 [pico/evaluation/evaluator.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/evaluation/evaluator.py) 中：

`FakeModelClient` 接受一组预设的 Response/Tool 调用序列，逐步喂给 Pico Runtime 调度引擎。

通过 `FakeModelClient`，我们可以 100% 验证：
- 工具参数解析与风险拦截逻辑是否正确。
- 断点恢复后状态与漂移检测是否正常。
- 重复工具调用 (`Repeated Tool Guard`) 是否被成功阻断。

**收益**：只要回放失败，100% 确定是 Harness 框架逻辑出 Bug，而不是模型“抽风”。

## 3. 评测 4 维通过判定标准 (Pass Criteria)

单次 benchmark 任务的成功判定由 4 维硬性条件共同决定：

| 判定维度 | 说明 |
| :--- | :--- |
| **1. `verifier_passed`** | 验证脚本执行结果 `exit_code == 0`（如自动跑 pytest 单元测试全通过）。 |
| **2. `expected_artifact_exists`** | 预期生成的目标代码或配置文件真实存在于物理文件系统中。 |
| **3. `within_budget`** | 耗费的 Step 步数在预算限制之内（默认 `step_budget = 30`）。 |
| **4. `non_failure_stop_reason`** | 任务正常以 `completed` 结束，未因为 `step_budget_exceeded` 或未处理异常而中断。 |

## 4. 三大消融实验 (Ablation Studies)

通过控制变量法，分析各个核心功能对 Harness 性能的提升贡献：

1. **Context 压缩消融实验**：
   - **对照**：关闭 `CompactManager`。
   - **指标**：对比长对话下的 Token 溢出率与 Prompt Caching 命中率。
2. **Memory 召回消融实验**：
   - **对照**：禁用 `LayeredMemory` 与召回注入。
   - **指标**：对比模型找到特定仓库约定所需的工具调用步数 (`tool_steps`) 变化。
3. **Recovery 恢复消融实验**：
   - **对照**：禁用 Checkpoint 恢复与漂移校验。
   - **指标**：模拟外部修改文件后恢复 Session，评估 Agent 的任务成功率。
