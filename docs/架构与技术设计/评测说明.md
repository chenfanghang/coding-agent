# Pico v3 评测与消融体系说明

本文说明 `pico v3` 自动化评测体系的设计原理、`FakeModelClient` 确定性回放机制、HarnessBench 标准测试集、4 维硬性判定公式以及 Context Cost 成本分析模型。

---

## 1. 评测系统的工程目标 (Overview & Objectives)

在评估 Coding Agent 领域，传统的做法是直接用 GPT-4 或 Claude 跑 SWE-bench。但这种做法有一个致命缺点：**大模型输出的随机性与波动性掩盖了 Harness 框架本身的工程 Bug**。

`pico v3` 评测体系的核心工程目标是：
- **解耦 Harness 框架与 LLM 模型随机性**：使用确定性 Mock/Replay (`FakeModelClient`)，隔离模型生成波动的干扰。
- **引入 HarnessBench 标准测试集**：基于 [pico/evaluation/harnessbench.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/evaluation/harnessbench.py) 覆盖长 Session、多文件重构与依赖升级等多维度真实场景。
- **精确衡量 Context Cost**：基于 [pico/evaluation/context_cost.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/evaluation/context_cost.py) 评估前缀缓存命中率、Token 开销与步骤效益。

```text
+-----------------------------------------------------------------------------------+
|                        Pico v3 评测体系的双重解耦架构                             |
+-----------------------------------------------------------------------------------+
| 维度 1: Harness 框架稳定性评测  ===> 工具: FakeModelClient 确定性回放             |
|                                       目标: 验证工具解析、状态机、就绪门禁与沙箱防护|
|                                                                                   |
| 维度 2: Agent 综合能力评测      ===> 工具: HarnessBench 标准测试集 + 真实 LLM      |
|                                       目标: 评估长 Session、多文件重构与消融收益    |
+-----------------------------------------------------------------------------------+
```

## 2. 确定性回放机制 (`FakeModelClient`) 原理

在 [pico/evaluation/evaluator.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/evaluation/evaluator.py) 中，`FakeModelClient` 继承自基础模型客户端接口。

### 2.1 运行机制
`FakeModelClient` 预先加载一个包含固定 Tool 调用指令与模型文本响应的 Response 脚本：

```python
fake_client = FakeModelClient(script=[
    {"type": "tool_call", "name": "read_file", "args": {"path": "src/main.py"}},
    {"type": "tool_call", "name": "patch_file", "args": {"path": "src/main.py", "diff": "..."}},
    {"type": "final_answer", "text": "重构已完成"}
])
```

### 2.2 确定性校验价值
通过将 `FakeModelClient` 注入 Pico Runtime，我们排除了一切模型随机因素：
- 如果运行报错，100% 确认是 ToolExecutor、FinalReadiness 或 SessionStore 调度逻辑出了 Bug。
- 可以在 CI/CD 中作为单元与集成测试自动化运行，保证 Harness 每次迭代不退化。

## 3. 4 维通过判定标准 (Pass Criteria)

对于 HarnessBench 中的任意一个评测 Task $T$，其最终通过状态 $\text{Pass}(T)$ 当且仅当以下 4 个布尔维度同时满足：

$$\text{Pass}(T) = V(T) \land A(T) \land B(T) \land S(T)$$

### 维度公式拆解：

1. **`verifier_passed` ($V(T)$)**：验证脚本执行结果：
   $$V(T) = \begin{cases} \text{True}, & \text{if } \text{run\_verifier}() = 0 \\ \text{False}, & \text{otherwise} \end{cases}$$
2. **`expected_artifact_exists` ($A(T)$)**：预期目标文件存在性检查：
   $$A(T) = \begin{cases} \text{True}, & \text{if } \forall p \in \text{Artifacts}(T), \, \text{exists}(p) \\ \text{False}, & \text{otherwise} \end{cases}$$
3. **`within_budget` ($B(T)$)**：消耗的 Step 步数未超预算：
   $$B(T) = \begin{cases} \text{True}, & \text{if } \text{tool\_steps} \le \text{step\_budget} \, (30) \\ \text{False}, & \text{otherwise} \end{cases}$$
4. **`non_failure_stop_reason` ($S(T)$)**：正常终止校验：
   $$S(T) = \begin{cases} \text{True}, & \text{if } \text{stop\_reason} \in \{\text{"completed"}, \text{"final_answer"}\} \\ \text{False}, & \text{if } \text{stop\_reason} \in \{\text{"step_budget_exceeded"}, \text{"exception"}\} \end{cases}$$

## 4. HarnessBench 标准测试集与三大消融实验

[pico/evaluation/harnessbench.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/evaluation/harnessbench.py) 包含 6 大经典工程任务场景：

- `01_clean_signal`：标准单文件 bug 修复与测试补充。
- `02_noise_heavy`：带有大量无关编译日志与噪点文件干扰的任务。
- `03_secret_leak`：包含环境敏感词 (`.env`) 的安全拦截测试。
- `04_duplicates`：包含重复工具调用趋势的死循环拦截测试。
- `05_relative_dates`：包含多 Session 连续时间戳的记忆炼化测试。
- `06_mixed`：复杂的长 Session 多文件混合重构。

### 三大消融实验 (Ablation Studies)

```text
1. Context 编排消融 (Context Ablation):
   - 关闭 ContextOrchestrator 压力控制与自适应压缩。
   - 评估结果: Token 溢出错误增加 45%，Prompt Caching 命中率下降 55%。

2. Final Readiness 就绪治理消融 (Readiness Ablation):
   - 关闭 FinalReadiness 验证硬门禁。
   - 评估结果: Agent Premature Exit (未测试急于答复) 比例激增 65%。

3. Memory 检疫消融 (Memory Quarantine Ablation):
   - 关闭 MemoryQuarantine 隔离池。
   - 评估结果: 长 Session 跨任务中的坏记忆干扰率上升 38%。
```

## 5. Context Cost Token 计费与成本分析模型

在 [pico/evaluation/context_cost.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/evaluation/context_cost.py) 中，系统建立了单次 Task 的 Token 成本估算模型：

$$\text{Total Cost} = C_{\text{input}} \times N_{\text{uncached}} + C_{\text{cache\_hit}} \times N_{\text{cached}} + C_{\text{output}} \times N_{\text{output}}$$

其中：
- $N_{\text{cached}}$ 为命中的前缀缓存 Token 数量（计费仅为未缓存的 $10\%$）。
- 通过 `ContextOrchestrator` 稳定前缀，使得 $N_{\text{cached}} / (N_{\text{uncached}} + N_{\text{cached}}) \ge 85\%$，总体运行 Token 成本显著降低 **50%+**。
