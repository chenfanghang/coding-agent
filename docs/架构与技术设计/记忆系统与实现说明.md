# Pico v3 记忆系统与算法实现说明

本文说明 `pico v3` 记忆系统的整体设计目标、架构选型对比、四层数据协议、打分召回算法、Memory Quarantine (记忆检疫池) 机制与 Auto-Dream 后台并发控制原理。

---

## 1. 系统概述与设计目标 (Overview & Objectives)

在 Coding Agent 运行过程中，频繁的长会话交互会产生大量上下文。记忆系统（Memory System）的核心使命是：**在有限的 Context 窗口内，跨 Session 留存仓库约定、架构决策与用户偏好，同时提供文件感知的即时工作状态**。

Pico v3 记忆系统的核心工程目标包括：
- **跨 Session 知识持久化**：自动积累并炼化长期规则与偏好。
- **< 1ms 超低检索延时**：在单步 ReAct 迭代前完成即时上下文注入。
- **零额外部署依赖**：不依赖外部向量数据库或重型后台服务。
- **透明可追溯**：记忆全量以人类可读的 Markdown/JSON 文件落盘。

---

## 2. 架构决策与选型对比 (Architectural Decisions & Trade-offs)

在设计 Pico v3 记忆系统时，我们针对业内常见的 **向量数据库 (Vector DB/RAG)** 方案进行了第一性原理拆解，对比矩阵如下：

| 比较维度 | Pico v3 分层文件记忆 | 传统 Vector DB (RAG) | 工程分析与决策理由 |
| :--- | :--- | :--- | :--- |
| **1. 代码精确度** | 基于 Tag 与 Exact Keyword 精确匹配，零无关干扰 | 基于向量语义距离，对变量名与正则易召回错误干扰段落 | Coding 场景需精密定位，标量与词条匹配胜出 |
| **2. 本地依赖开销** | 零依赖，直接读写本地原生 Markdown 文件 | 绑定 Chroma/Milvus，增加 50MB+ 依赖包与 200MB+ 内存 | CLI 工具需轻量自包含，拒绝过度工程化 |
| **3. 文件变动成本** | 仅更新文件元数据摘要，< 1ms 无延迟 | 频繁修改代码需重新 Embedding 切片，CPU 消耗极大 | 代码频繁修改场景下 RAG 重新切片成本不可接受 |
| **4. 可控性与可读性** | 明文 Markdown，人类可直接编辑、修正或擦除 | 向量黑盒，难以直接调试、手动修正或干预 | 开发者拥有 100% 的数据掌控力 |

综合以上考量，Pico v3 选择了 **分层 Markdown 结构 + Tag 算分召回 + Memory Quarantine 检疫隔离池** 的架构路线。

## 3. 四层记忆数据模型与文件协议 (Data Model & Protocols)

Pico v3 将记忆按生命周期与作用域划分为四层结构：

```text
.pico/memory/
├── MEMORY.md                       # 1. 长期记忆大纲索引 (< 200 行，固定进 Prompt)
├── topics/                         # 2. Durable Memory (4 类主题 Markdown)
│   ├── user-preferences.md         #    - 用户角色与协作偏好
│   ├── project-conventions.md      #    - 仓库约定与命名规范
│   ├── key-decisions.md            #    - 重大架构决策与理由
│   └── dependency-facts.md         #    - 关键依赖版本与踩坑记录
├── logs/                           # 3. Daily Logs (只增不减 append-only)
│   └── YYYY/MM/YYYY-MM-DD.md       #    - 按天追加的原始观察日志
├── quarantine/                     # 4. Quarantine 隔离池 (存放待校验候选记忆)
└── .consolidate-lock               # auto-dream PID 互斥锁与时间戳
```

### 3.1 协议格式定义

- **Working Memory** (`session["memory"]`)：
  ```json
  {
    "task_summary": "正在重构 authentication 模块的 JWT 校验逻辑",
    "recent_files": ["src/auth.py", "tests/test_auth.py"],
    "file_summaries": {
      "src/auth.py": {
        "freshness": "a3f89e...",
        "summary": "包含 verify_jwt() 与 generate_token() 函数"
      }
    }
  }
  ```
- **Durable Topics Markdown 规范**：
  ```markdown

  ## [pytest-xdist] 并发测试规范
  - created_at: 2026-06-01T10:00:00Z
  - tags: [pytest, testing, concurrency]
  - content: 本仓库所有单元测试强制使用 pytest -n auto 运行。
  ```

## 4. 动态相关记忆召回算法 (`retrieval_candidates`) 通俗解析

在每轮 Prompt 组装时，系统需要从长期记忆中自动挑选出与当前用户输入最相关的 3 条记忆。这个挑选过程由 [pico/features/memory.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/features/memory.py) 中的 `retrieval_candidates` 函数完成。

### 4.1 算法核心逻辑（三级过滤器）

整个召回算法的打分规则非常直观，遵循 **“三级优先级降序”** 的原则：

```text
[用户输入 Prompt 分词]
         │
         v
 ┌──────────────────────────────────────────────────────────┐
 │ 1. 优先看标签匹配 (Exact Tag Match)                      │
 │    用户的词是否精准击中了记忆卡片上的 tags 标签？       │
 └─────────────────────────┬────────────────────────────────┘
                           │
                           v
 ┌──────────────────────────────────────────────────────────┐
 │ 2. 次要看关键词重叠数 (Keyword Overlap Count)            │
 │    如果标签都没命中或都命中了，看正文与标题里重合的词数量 │
 └─────────────────────────┬────────────────────────────────┘
                           │
                           v
 ┌──────────────────────────────────────────────────────────┐
 │ 3. 同分看新鲜度 (Recency)                                │
 │    如果重叠词数量也一样，优先选择更新时间最新的记忆     │
 └──────────────────────────────────────────────────────────┘
```

### 4.2 真实案例一步步打分推演

假定用户在终端输入了命令：“**如何配置项目的 pytest 并发单元测试？**”

系统将用户输入分词提取出核心词集：`{"pytest", "并发", "单元测试", "配置"}`。

此时记忆库中有以下 3 条候选笔记：

| 候选笔记编号 | 笔记标题与内容 | 绑定的 Tags 标签 | 创建时间 |
| :--- | :--- | :--- | :--- |
| **笔记 A** | `## [pytest-xdist] 并发测试规范`<br>本仓库测试强制使用 pytest -n auto | `[pytest, testing]` | 2026-06-01 |
| **笔记 B** | `## [pytest] 单端调试命令`<br>单个测试使用 pytest tests/test_auth.py | `[pytest]` | 2026-06-15 |
| **笔记 C** | `## [docker] 容器构建规范`<br>Docker 镜像构建需配置并发编译参数 | `[docker, build]` | 2026-05-20 |

#### 打分过程与比对结果：

1. **计算标签匹配 (`exact_tag_match`)**：
   - 笔记 A 的标签 `pytest` 命中用户词集 $\rightarrow$ **命中 (得分 1)**。
   - 笔记 B 的标签 `pytest` 命中用户词集 $\rightarrow$ **命中 (得分 1)**。
   - 笔记 C 的标签 `[docker, build]` 未命中用户词集 $\rightarrow$ **未命中 (得分 0)**。
2. **计算关键词重叠数 (`keyword_overlap`)**：
   - 笔记 A 的文本包含 `pytest`, `并发`, `测试` $\rightarrow$ **重叠词数 = 3**。
   - 笔记 B 的文本包含 `pytest`, `测试` $\rightarrow$ **重叠词数 = 2**。
   - 笔记 C 的文本包含 `并发` $\rightarrow$ **重叠词数 = 1**。
3. **结合时间戳生成元组 `(标签得分, 词重叠数, 时间戳)`**：
   - 笔记 A 的综合打分元组：`(1, 3, 20260601)`
   - 笔记 B 的综合打分元组：`(1, 2, 20260615)`
   - 笔记 C 的综合打分元组：`(0, 1, 20260520)`

#### 最终排序输出：
Python 对元组进行降序排列后，得出最终排名：
**笔记 A `(1, 3, ...)` > 笔记 B `(1, 2, ...)` > 笔记 C `(0, 1, ...)`**

系统自动截取 Top-2（笔记 A 和 笔记 B）注入到 Prompt 中：

```markdown
## Relevant Durable Memories (2 candidate matches)
- [project-conventions] [pytest-xdist] 本仓库测试强制使用 pytest -n auto
- [project-conventions] [pytest] 单个测试使用 pytest tests/test_auth.py
```

这样既避免了加载无关的 笔记 C (Docker 容器)，又在 **< 1ms** 内精准锁定了并发测试规范！

## 5. 记忆检疫隔离与数据治理 (Quarantine & Data Governance)

为了防止模型在对话中产生的幻觉或错误格式污染物理数据库，Pico v3 引入了 [pico/features/memory_quarantine.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/features/memory_quarantine.py) 与 [pico/features/memory_lint.py](file:///Users/chenfanghang/PycharmProjects/pico/pico/features/memory_lint.py)：

```text
[模型回答中的 <memory> 标签]
           │
           v
[memory_lint.py: 格式与合法性校验]
     ├── 包含畸形 Tag / 敏感 Key (如 API Key)? ---> 丢弃阻断
     └── 校验合法 -> 送入检疫池
           │
           v
[memory_quarantine.py: 冲突检测]
     ├── 与已有 Durable Topics 存在冲突事实? ----> 写入 .pico/memory/quarantine/ 暂存
     └── 无冲突事实 --------------------------> 写入 Daily Logs
```

## 6. 后台归纳与并发控制 (Auto-Dream & Concurrency Control)

`auto-dream` 后台守护线程定期将 Daily Logs 与 Quarantine 隔离池中的记录归纳炼化为 Durable Topics。

### 6.1 启动门禁 (`evaluate_auto_dream_gate`)
- 距离上次炼化时间 $\Delta t \ge 24 \text{ 小时}$。
- 自上次炼化以来累积的会话数量 $N_{\text{session}} \ge 5$。

### 6.2 基于 PID 的跨进程文件互斥锁

系统在 `.pico/memory/.consolidate-lock` 上实现了 PID 锁，防止主进程与后台 Dream 线程并发修改 `MEMORY.md` 引起物理文件损坏：

```python
def acquire_lock(memory_dir):
    lock_path = memory_dir / ".consolidate-lock"
    current_pid = os.getpid()
    if lock_path.exists():
        stat = lock_path.stat()
        age = time.time() - stat.st_mtime
        holder_pid = int(lock_path.read_text().strip())
        if age < HOLDER_STALE_S:  # 若锁未超时 (如 < 300s)
            try:
                os.kill(holder_pid, 0)  # 探测持锁进程是否仍然存活
                return False            # 锁有效且被持有着，抢锁失败
            except OSError:
                pass                    # 持锁进程已崩溃，允许清理坏锁
    lock_path.write_text(str(current_pid))
    return True
```
