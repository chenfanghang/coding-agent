# Pico 实验评测说明

> 面向用户与技术面试的项目说明  
> 实验模型：DeepSeek `deepseek-v4-pro`  
> 实验日期：2026-07-28

## 一、项目速读

Pico 是一个本地 Coding Agent。它不仅要让大模型“回答代码问题”，还要让模型在真实工程环境中安全、连续、可验证地完成任务。

一个可用的 Coding Agent 至少要解决五类问题：

1. 模型能否正确读取、修改和验证代码；
2. 长会话中能否控制上下文规模；
3. 中断后能否恢复任务，而不是从头开始；
4. 历史记忆能否真正提高效率，而不是引入错误；
5. 即使模型发出危险调用，Runtime 能否强制执行安全边界。

因此，Pico 的评测不是只看一个“任务通过率”，而是同时检查：

- 功能是否可用；
- 结果是否正确；
- 过程是否可审计；
- 成本是否下降；
- 安全边界是否生效；
- 模块收益能否从离线实验迁移到真实模型。

## 二、当前评测包含什么

### 1. 基础代码质量

包含 Ruff 和全量 Pytest。

这部分验证代码本身有没有回归、无效导入和明显的工程质量问题。

它回答：

> 项目代码是否稳定、可维护，已有行为是否被破坏？

它不评价 DeepSeek 的能力。

### 2. 真实用户场景

包含 50 个真人 CLI、REPL、PTY 场景，以及 Gate8 和业务 Dogfood。

这些场景像真实用户一样启动 Pico，执行计划、工具调用、代码修改、测试、Skill、子 Agent、Session Resume 和安全拒绝。

它回答：

> 用户实际使用 Pico 时，完整链路能不能工作？

这里不只检查最终回答，还会检查：

- 文件是否真的发生变化；
- 测试是否真的执行；
- 工具是否按策略被允许或拒绝；
- Report、Trace 和 Session Events 是否完整；
- 中断后是否能正确续接。

### 3. 固定 Benchmark

包含 12 个确定性任务，覆盖文本编辑、工具边界、恢复和 Durable Memory。

固定 Benchmark 使用预设模型输出，排除远程模型波动。

它回答：

> Pico Runtime、工具系统和证据链本身是否稳定？

这类测试适合发现代码回归，但不能代表 DeepSeek 的能力上限。

### 4. 上下文实验

上下文实验比较启用和关闭 Context Orchestrator 后的 Prompt 大小、请求保留和任务质量。

它回答：

> Pico 能否减少低价值上下文，同时保留当前任务所需信息？

这直接关系到：

- 长会话可持续性；
- 模型上下文压力；
- Token 消耗；
- 潜在调用成本。

### 5. 记忆实验

记忆实验包含 Memory On、Memory Off、无关记忆、冲突事实、过期事实、秘密信息和真实 DeepSeek 矩阵。

它回答：

> 记忆是否真的让模型更准确、更少重复读取，而不是让模型被旧信息误导？

评价记忆不能只看“召回了多少”，还要检查：

- 召回内容是否正确；
- 冲突时是否会拒绝猜测；
- 是否使用过期事实；
- 是否泄漏秘密；
- 是否减少工具调用；
- 真实模型下是否仍有收益。

### 6. 恢复实验

恢复实验模拟任务执行到一半后中断，或者恢复时 workspace 已经变化。

它回答：

> Pico 能否安全地继续未完成任务，而不是重复操作或基于过期状态继续？

主要检查：

- Checkpoint 恢复；
- Stale 文件重新读取；
- Workspace Drift 检测；
- Todo 连续性；
- 恢复后的第一个动作是否正确。

### 7. 安全与权限实验

安全实验覆盖路径逃逸、符号链接逃逸、只读模式、审批拒绝、Sandbox、非法参数和秘密脱敏。

它回答：

> 即使模型发出错误或危险调用，Runtime 能否强制拒绝并留下审计证据？

这里强调的是 Runtime 强制约束，而不是依赖模型“自觉安全”。

### 8. Dream 长期记忆实验

Dream 把每日记录和会话内容整理为长期 Topic Memory。

它回答：

> Pico 能否保留有效信息、删除噪声、合并重复事实并拒绝秘密内容？

### 9. LLM Handoff 实验

Handoff 让模型生成结构化交接摘要，用于长会话压缩。

实验比较：

- 确定性 Compact；
- LLM Handoff Compact。

它回答：

> 额外调用一次模型生成摘要，能否在不降低任务质量的前提下降低后续上下文成本？

因此不能只看价格，还必须同时看总 Token、缓存、成功率、Verifier 和任务终止状态。

## 三、为什么要做分层评测

Coding Agent 的评测很容易出现一个误区：用单一任务通过率概括全部能力。

但不同实验实际上回答不同问题：

| 实验 | 能说明什么 | 不能单独说明什么 |
|---|---|---|
| Ruff/Pytest | 代码和已有行为是否稳定 | 真实模型是否好用 |
| 固定 Benchmark | Runtime 合同是否可靠 | DeepSeek 是否能完成开放任务 |
| 真人场景 | 产品完整链路是否可用 | 某个模块是否产生因果收益 |
| 上下文消融 | Prompt 是否变小 | 最终账单是否一定下降 |
| 记忆消融 | 机制是否减少重复工作 | 真实模型下是否仍然有效 |
| 恢复消融 | Checkpoint 是否改善续接 | 所有中断都能恢复 |
| 安全实验 | Runtime 是否执行边界 | 模型本身是否稳定遵循要求 |
| Handoff | 是否存在成本优化潜力 | 是否已经实现稳定降本 |

Pico 的评测采用四层证据：

```text
L1 代码质量
  -> L2 产品行为
  -> L3 确定性机制验证
  -> L4 真实模型收益验证
```

只有 L4 的真实模型结果，才能用于判断某个功能是否真正产生产品收益。

## 四、核心结果

### 总体结果

| 评测项 | 规模 | 结果 |
|---|---:|---:|
| Pytest | 515 项 | 513 通过，2 跳过，0 失败 |
| Ruff | 全仓库 | 8 个静态检查问题 |
| 真人场景 | 50 个 | 50/50 通过 |
| Gate8 | 9 个 | 9/9 通过 |
| 业务 Dogfood | 3 个场景 | 3/3、26/26 检查通过 |
| 固定 Benchmark | 12 个任务 | 12/12 通过 |
| Memory Challenge | 55 个案例 | 52/55 通过 |
| Dream Quality | 6 个案例 | 6/6 通过 |
| Memory Fidelity | 5 个案例 | 5/5 通过 |
| Handoff | 5 对任务 | 尚未达到稳定收益门槛 |

### 一句话结论

> Pico 的核心功能、DeepSeek 端到端链路、上下文编排和恢复能力表现良好；但真实记忆收益没有成立，LLM Handoff 也还不能宣称稳定降本。

## 五、关键实验一：上下文压缩

### 为什么做

Coding Agent 的 Prompt 会不断累积：

- 系统提示；
- Workspace 信息；
- 历史对话；
- 工具结果；
- Memory；
- Skills；
- 当前请求。

如果不管理上下文，长会话会越来越慢、越来越贵，也可能超过模型窗口。

### 怎么做

实验组合了三种 History 长度、两种 Memory 数量和两种当前请求长度，共 12 个配置，每个配置重复 5 次。

对比：

- 未压缩的 Raw Prompt；
- 启用 Context Orchestrator 的 Prompt。

### 结果

DeepSeek 真实实验：

| 指标 | 原始 | 优化后 |
|---|---:|---:|
| 平均 Prompt 字符数 | 13,450 | 11,982.67 |
| 平均减少 | — | 10.91% |
| 最大减少 | — | 19.68% |
| 当前请求保留率 | — | 100% |

### 如何理解

这是本轮最明确的真实性能提升：

- Prompt 平均减少约 10.91%；
- 当前用户请求没有被压缩丢失；
- 最大配置接近 20% 的缩减。

但最差配置出现 -0.86%，说明短上下文下编排元数据可能比节省量更大。下一步应优化触发阈值，而不是所有场景都强制压缩。

## 六、关键实验二：记忆

### 为什么做

记忆功能的目标不是“存得越多越好”，而是：

- 后续任务能直接使用正确历史事实；
- 减少重复读取；
- 避免使用过期或冲突信息；
- 不暴露秘密；
- 最终提高正确率和效率。

### 离线实验结果

| Variant | 正确率 | 重复读取 | 平均工具步数 |
|---|---:|---:|---:|
| Memory On | 100% | 0 | 0 |
| Memory Off | 100% | 60 | 1 |
| Irrelevant Memory | 100% | 60 | 1 |

离线环境中，Memory On 将重复读取从 60 降到 0，同时保持 100% 正确率。

这证明记忆机制在确定性条件下按设计工作。

### DeepSeek 真实结果

| Variant | 正确率 | 重复读取 | 平均工具步数 |
|---|---:|---:|---:|
| Memory On | 75.00% | 73 | 1.22 |
| Memory Off | 100.00% | 55 | 0.92 |
| Irrelevant Memory | 86.67% | 84 | 1.40 |

### 关键发现

真实模型结果与离线结果相反：

- Memory On 正确率下降 25 个百分点；
- 重复读取从 55 增加到 73；
- 工具步骤和模型尝试次数也增加。

失败主要集中在精确编辑和历史引用任务。

这说明：

> 记忆模块本身实现正确，不等于真实模型使用这些记忆后一定获得收益。

可能原因包括：

- 记忆摘要和当前文件状态存在冲突；
- 模型过度相信记忆，跳过必要验证；
- 注入的信息增加了决策歧义；
- 精确代码编辑不能仅依赖摘要。

因此，当前不能对外宣称“记忆提升了真实模型效率”。

## 七、关键实验三：冲突事实处理

Memory Challenge 共 55 个案例，通过 52 个。

三个失败都属于同一问题：

```text
存在两个冲突事实
  + 没有明确的新旧或 supersede 关系
  -> 系统仍选择其中一个
  -> 正确行为应该是回答 unknown
```

例如：

- 两个不同的 Deployment Owner；
- 两种不同的 Command Runner；
- 两个不同的 Report Owner。

这说明系统的 Recall 很强，但冲突消解不够谨慎。

后续设计应加入明确规则：

```text
同一属性出现冲突值
  -> 比较时间和 supersede 关系
  -> 无法确定有效值
  -> 标记 ambiguous
  -> abstain 或询问用户
```

这个结果体现了评测的价值：它没有只证明系统“召回到了信息”，还检查召回的信息是否足以支持确定结论。

## 八、关键实验四：任务恢复

### 为什么做

Coding Agent 的任务可能因网络、进程退出、用户暂停或上下文切换而中断。

恢复机制需要避免：

- 从头重复工作；
- 使用过期文件状态；
- 丢失 Todo；
- 在 Workspace 已变化时错误续跑。

### 结果

| 指标 | 不启用恢复 | 启用恢复 |
|---|---:|---:|
| Resume 成功率 | 0% | 90% |
| Stale Re-anchor | 0% | 100% |
| Workspace Drift 检测 | 0% | 100% |
| 首个动作正确率 | 0% | 100% |
| Todo 连续性 | 0% | 100% |
| 错误接受率 | 0% | 0% |

### 如何理解

恢复能力是明确的功能提升：

- 中断后能够继续原任务；
- 文件变化后能够重新定位；
- Todo 和首个动作保持连续；
- 无效 Checkpoint 不会被错误接受。

整体恢复成功率是 90% 而不是 100%，主要受缺失 Checkpoint 等本身不可恢复的场景影响。

## 九、关键实验五：安全与 Dream

### 安全

实验覆盖：

- Path Escape；
- Symlink Escape；
- Read-only 写入；
- Approval Denied；
- Sandbox；
- 非法参数；
- 重复工具调用；
- Secret Redaction。

核心设计原则是：

> 安全边界由 Runtime 强制执行，不能依赖模型自觉。

真实安全矩阵执行了 33 次调用，观察到 Path Escape、Tool Policy、Invalid Arguments、Tool Not Allowed 等拒绝事件。

当前不足是安全矩阵缺少统一的逐条 Pass/Fail 字段。下一步需要分别验证：

1. 模型是否真的触发目标工具路径；
2. Runtime 是否用预期错误码拒绝。

### Dream

Dream Quality 6/6 通过：

- 有效信息保留率 100%；
- 噪声拒绝率 100%；
- Secret 拒绝率 100%；
- 重复事实合并率 100%；
- 相对日期转换率 100%。

说明长期记忆整理本身表现良好。当前记忆问题主要出现在模型如何使用记忆，而不是 Dream 的过滤和整理阶段。

## 十、关键实验六：LLM Handoff

### 为什么做

长会话中可以通过交接摘要减少历史上下文。LLM Handoff 额外调用一次模型，生成结构化任务摘要。

问题是：额外调用本身也有成本，所以必须证明它带来的后续节省大于自身开销。

### 结果

| 指标 | LLM Handoff | 确定性 Compact |
|---|---:|---:|
| 任务成功率 | 60% | 40% |
| Verifier 通过率 | 80% | 60% |
| 平均总输入 Token | 27,298 | 26,928 |
| 平均可计费输入 Token | 8,438 | 13,284 |
| 平均工具步数 | 18.0 | 16.6 |
| 平均模型尝试 | 8.8 | 7.4 |

其他结果：

- 可计费输入 Token 约下降 36.5%；
- 配置价格中位下降 26.63%；
- 总输入 Token 增加 1.37%；
- 出现 2 个质量退化；
- `claimable_cost_win=false`。

### 如何理解

Handoff 有潜力：

- 缓存后的可计费输入减少；
- 本轮任务成功率和 Verifier 通过率有所提高。

但还不能声明稳定收益：

- 总输入 Token 没有下降；
- 工具步骤和模型尝试增加；
- 出现质量退化；
- 部分任务以 `stopped` 结束；
- 当前只有一轮 5 对任务的样本。

工程上应坚持：

> 成本下降、质量不退化、任务正常结束三个条件必须同时成立，才能宣称优化有效。

## 十二、这个项目体现了哪些工程能力

### 1. 不只关注最终答案

评测同时记录：

- 最终任务结果；
- 工具调用过程；
- 权限决策；
- 安全事件；
- Session；
- Trace；
- Report；
- Verifier。

这让 Agent 的行为可解释、可审计、可复现。

### 2. 能区分机制正确和产品有效

离线 Memory 实验非常好，但真实 DeepSeek 结果退化。

项目没有用离线数据掩盖真实问题，而是明确区分：

- 机制是否按设计工作；
- 真实模型是否因此获益。

### 3. 使用消融实验验证因果关系

通过 Memory On/Off、Resume On/Off、Deterministic/Handoff 等对照，判断性能变化是否真的由目标模块造成。

### 4. 对成本指标保持谨慎

虽然 Handoff 配置价格下降，但总 Token 和质量没有同时改善，因此没有将其包装成“成本优化成功”。

### 5. 把失败结果转化为下一步设计

实验识别出三个具体方向：

- 冲突事实需要 abstain；
- 精确编辑不能过度依赖 Memory；
- Context 和 Handoff 应按收益动态触发，而不是固定启用。

## 十三、面试中如何介绍这个项目

### 90 秒项目介绍

> Pico 是我做的一个本地 Coding Agent。这个项目的重点不只是接入大模型，而是让 Agent 在真实工程环境中安全、连续、可验证地完成任务。  
>   
> 我为它设计了四层评测体系：第一层是 Pytest 和静态检查，验证代码质量；第二层是 50 个真实 CLI、REPL、工具和恢复场景，验证产品链路；第三层用确定性消融验证上下文、记忆和恢复机制；第四层接入 DeepSeek，验证这些机制是否真的带来正确率、效率和成本收益。  
>   
> 结果上，513 个测试通过，50 个真人场景全部通过。上下文编排让真实 Prompt 平均减少约 10.9%，恢复成功率从 0 提升到 90%，Workspace Drift 检测达到 100%。但我也发现一个很关键的反直觉结果：记忆在离线实验中把重复读取从 60 降到 0，但接入真实 DeepSeek 后，正确率反而从 100% 降到 75%。这说明模块实现正确不等于产品收益成立。  
>   
> 所以后续我没有继续堆功能，而是把优化重点放在冲突事实 abstain、记忆与当前文件状态的优先级，以及 Handoff 的动态收益门槛上。这个项目让我建立了一套比较完整的 Agent 评测和工程化方法。

### 30 秒精简版

> Pico 是一个本地 Coding Agent。我重点解决的是长会话上下文、任务恢复、记忆和安全执行问题。项目有四层评测：代码回归、50 个真人场景、确定性消融和 DeepSeek 真实实验。当前核心链路全部通过，上下文平均压缩约 10.9%，恢复成功率达到 90%；同时真实实验发现 Memory On 正确率只有 75%，说明离线收益没有直接迁移。我把这个负向结果进一步定位到冲突事实和精确编辑场景，并据此设计下一轮优化。

## 十四、高概率面试追问

### 追问 1：为什么不能只看任务通过率？

推荐回答：

> Coding Agent 的失败可能来自模型、Runtime、工具策略、上下文、权限或 Verifier。单一通过率无法定位原因，也容易把偶然成功当成系统能力。所以我把评测拆成代码质量、产品行为、确定性机制和真实模型四层，并保存 Trace、Report 和工具事件。这样既能看最终结果，也能解释为什么成功或失败。

面试官想验证：

- 是否理解 Agent 是一个系统，而不只是一次模型调用；
- 是否具备评测分层和故障归因能力。

### 追问 2：为什么离线记忆很好，真实模型反而退化？

推荐回答：

> 离线实验使用固定模型输出，证明 Memory 的检索和注入机制按设计工作；但真实模型会对额外上下文做自主判断。Memory 可能和当前文件状态冲突，也可能让模型过度相信摘要、跳过必要读取。真实实验中失败集中在精确编辑和历史引用任务，所以我认为问题不在“能不能召回”，而在证据优先级和模型使用策略。下一步会保存每条失败的 Prompt、Selected Memory 和当前文件状态，做逐任务归因。

面试官想验证：

- 是否能解释离线与线上差异；
- 是否会基于证据定位问题，而不是泛泛归因于模型不稳定。

### 追问 3：如何判断上下文压缩是否有效？

推荐回答：

> 不能只看 Prompt 变短。我会同时检查压缩比例、当前请求保留、任务成功率、Verifier、总输入 Token，以及压缩调用本身的成本。Pico 的真实上下文实验平均减少约 10.9%，当前请求保留率 100%，这部分可以认为有效。但个别配置出现 -0.86%，说明短上下文时不应该强制启用，需要动态触发。

### 追问 4：为什么 Handoff 价格下降却不算优化成功？

推荐回答：

> 因为配置价格下降主要来自缓存后的可计费输入减少，但总输入 Token反而增加了 1.37%，同时出现两个质量退化，工具步数和模型尝试也更多。我设定的标准是成本、质量和终止状态必须同时改善，因此最终保持 `claimable_cost_win=false`。这可以避免只挑有利指标得出错误结论。

### 追问 5：Agent 安全为什么不能依赖 Prompt？

推荐回答：

> Prompt 只能降低模型发出危险调用的概率，不能形成强边界。Pico 把路径校验、只读限制、Approval、Sandbox 和 Secret Redaction 放在 Runtime。即使模型要求访问 workspace 外文件，工具层也必须拒绝，并把错误码和安全事件写入 Trace。这样安全性来自系统约束，而不是模型自觉。

### 追问 6：如果继续优化，你会先做什么？

推荐回答：

> 第一优先级是真实 Memory 退化。我会永久保存失败样本的 Prompt、Memory、文件状态和 Trace，优先复现 edit_token、history_tool 和 edit_field。第二是冲突事实 abstain，当两个值无法判断新旧时必须返回 unknown。第三是给 Context 和 Handoff 加动态收益门槛，只在预计净收益为正时触发。最后补充安全实验的逐条 Verifier 和延迟 P50/P95/P99。

## 十五、回答评分参考

### 好答案

- 先讲评测要解决的问题，再讲数据；
- 能区分离线机制和真实模型效果；
- 主动承认负向结果；
- 能解释指标之间的冲突；
- 给出基于证据的下一步实验；
- 不把配置价格下降直接说成真实降本。

### 普通答案

- 只罗列测试数量和通过率；
- 能说出结果，但无法解释为什么这样设计；
- 对失败只归因于“模型不稳定”；
- 没有对照实验或后续验证方案。

### 危险答案

- 把固定 Scripted Benchmark 当成真实模型能力；
- 宣称 Memory 已经提升真实效率；
- 宣称 Handoff 已经稳定节省成本；
- 忽略 Ruff、冲突事实和质量退化；
- 用没有 Verifier 的安全事件数量当作通过率。

## 十七、最终结论

Pico 当前已经证明：

- 核心 Coding Agent 链路可用；
- DeepSeek 能完成真实代码、工具和恢复场景；
- Context Orchestrator 能真实减少 Prompt；
- Checkpoint 和 Workspace Drift 检测能显著改善任务续接；
- Runtime 能执行工具和安全边界；
- 评测体系能够发现离线测试看不到的真实退化。

尚未证明：

- Memory 在真实模型下能稳定提高正确率；
- LLM Handoff 能稳定降低总成本；
- 所有安全场景都具备统一的真实模型通过率；
- Provider 长尾已经得到控制。

项目最有价值的地方，不是所有指标都漂亮，而是建立了一套能够区分“机制正确、产品可用和真实收益”的评测方法，并用真实实验发现了记忆和 Handoff 的边界。
