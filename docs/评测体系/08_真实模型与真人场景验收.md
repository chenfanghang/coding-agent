# 真实模型与真人场景验收

> Live 评测验证：确定性测试中成立的 Harness 机制，组合到真实 DeepSeek、CLI、REPL、Skills、多 Agent 和跨会话流程后，是否仍能形成可用的产品闭环。

---

## 1. 为什么还要做真人场景

固定响应适合定位 Harness 回归，但不会暴露以下问题：

- 模型是否理解工具返回的治理错误并主动修正策略。
- 模型是否会忽略已召回记忆并重复读取文件。
- 长会话中模型是否正确使用 Compact 或 Handoff 摘要。
- CLI、REPL、PTY、Skills 和多 Agent 的真实交互是否连通。
- Provider 错误响应和 Usage 元数据是否进入审计链路。

真实场景因此使用公共 CLI 驱动 Pico，并从外部检查 Workspace 与运行工件，避免测试代码直接操作 Runtime 内部状态。

---

## 2. Human50：50 个真人场景

入口：[`scripts/run_v3_human_scenario_gate.py`](../../scripts/run_v3_human_scenario_gate.py)

### 2.1 覆盖范围

| 能力域 | 代表场景 |
|---|---|
| 真实编码任务 | CRUD 脚手架、订单 Bugfix、发布审查、事故续接 |
| CLI / REPL / TUI | One-shot、Piped Input、`/help`、`/session`、`/usage` |
| Plan 与完成治理 | Active Plan、未规划禁止 Final、Plan 路径边界 |
| 文件与 Shell 治理 | Read-Before-Write、长输出落盘、审批与 Sandbox |
| Skills | 内置 Skill、项目 Skill、参数替换、Allowed Tools |
| 多 Agent | Explore 只读、Worker Scope、停止与续接 |
| 记忆与上下文 | Remember、Dream、Secret 拒绝、Compact |
| 恢复与 Provider | Workspace Mismatch、Profile 切换、错误审计 |
| 安全 | Path Traversal、Secret Redaction |

### 2.2 执行方式

```text
为场景创建独立临时 Workspace
        |
        v
通过 Pico CLI / PTY / REPL 发起真实请求
        |
        v
DeepSeek 与真实工具链执行
        |
        v
外部读取文件、Session、Trace 和 Report
        |
        v
逐项 Check 聚合为场景 Pass / Fail
```

输出目录必须位于 Pico 仓库之外，避免场景误发现父级 Git Root，破坏 Workspace 隔离。

### 2.3 当前结果

| 指标 | 结果 |
|---|---:|
| 场景数 | 50 |
| 通过 | 49 |
| 失败 | 1 |
| 通过率 | 98% |
| 失败场景 | S45 `secret-shaped 记忆拒绝` |

98% 表示当前 50 个已设计场景中的通过比例，不表示所有 Coding Agent 任务成功率为 98%。

## 3. Gate8：发布关键路径验收

入口：[`scripts/run_real_session_acceptance.py`](../../scripts/run_real_session_acceptance.py)

Gate8 使用更小、更稳定的关键路径集合进行发布前验收，覆盖 Bugfix、计划与子 Agent、Skill、Worker Scope、Resume、安全拒绝、上下文压力和 Provider 错误恢复；可选开启真实 Provider Smoke。

| 指标 | 当前结果 |
|---|---:|
| 场景数 | 9 |
| 通过 | 9 |
| 失败 | 0 |
| 通过率 | 100% |
| Live Provider Smoke | 通过 |
| 跳过项 | 0 |

这里的“9 个场景”包含本次运行启用的 Live Smoke；名称 Gate8 表示八条核心确定性验收路径，不应机械理解为输出永远只有八行。

## 4. 业务 Dogfood

入口：[`scripts/run_business_scenario_dogfood.py`](../../scripts/run_business_scenario_dogfood.py)

| 场景 | 主要能力 | 当前结果 |
|---|---|---:|
| 订单价格修复 | 定位、修改、测试闭环 | 通过 |
| 线上事故续接 | 跨会话恢复、重锚定与修复 | 通过 |

业务 Dogfood 比机制场景更接近用户目标，但当前只有 3 个任务，适合发现集成问题，不适合单独推导稳定总体成功率。

## 5. Live 运行的失败分类

| 类型 | 判定依据 | 报告方式 |
|---|---|---|
| Agent 能力失败 | 模型或工具轨迹没有完成任务 | 计入场景失败 |
| Harness 机制失败 | 错误放行、状态错乱、工件不一致 | 计入场景失败并定位模块 |
| Provider 基础设施失败 | 限流、网络、服务端超时 | 单独标记，不静默混入能力指标 |
| 评测环境失败 | Workspace、依赖或脚本异常 | 修复环境后重跑 |
| Verifier 设计失败 | 正确结果被误判或错误结果被放行 | 修复 Verifier 后整组重跑 |

---

## 6. 如何控制真实模型随机性

- 固定模型为 `deepseek-v4-flash`，避免不同型号混跑。
- 冻结任务 Prompt、初始 Workspace 和工具预算。
- 专项矩阵使用独立重复而不是只跑一次。
- 保存每次请求的 Trace、Report、Workspace 和 Provider Usage。
- 同时报告聚合结果和失败案例，不只展示最佳运行。
- 机制对比优先使用同任务配对实验。

## 7. 面试表达

> “确定性 Benchmark 之后，我还通过公共 CLI 做真实验收，避免测试直接操纵 Runtime 内部状态。Human50 覆盖 CLI、计划、工具治理、Skills、多 Agent、记忆、恢复和安全，当前 49/50 通过，失败的是 S45 Secret 记忆拒绝一致性。Gate8 用于发布关键路径，本轮 9/9 且 Live Provider Smoke 通过。业务 Dogfood 再用订单 Bugfix、事故续接和发布审查验证完整用户任务。这里我会把 98% 限定为当前 50 个设计场景的通过率，不泛化成任意 Coding Agent 任务成功率。”
