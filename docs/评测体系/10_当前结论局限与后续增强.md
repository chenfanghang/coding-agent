# 当前结论、局限与后续增强

> 高质量评测不仅报告通过项，也要说明数据可以支持到什么程度、还缺少哪些证据，以及下一轮实验如何提高结论可信度。

---

## 1. 当前可以确认的结论

### 1.1 Harness 合同稳定

12 个固定任务的任务通过率、Verifier 通过率和预算内完成率均为 100%。当前代码在固定响应下能够正确执行工具治理、恢复和 Durable Memory 合同。

### 1.2 上下文治理保留了任务正确性

离线压力矩阵当前请求保留率为 100%；DeepSeek Live 中 Raw 与 Full 正确率均为 100%，同时平均 Prompt 有所缩减。

### 1.3 记忆召回与安全边界有效

Memory Challenge 的 Evidence Recall@K 为 100%，陈旧事实使用率、Secret Exposure 和错误恢复接受率均为 0%。

### 1.4 恢复能够识别环境变化

开启 Resume 后，Workspace Drift 识别率和陈旧状态重锚定率均为 100%，关闭 Resume 时对应能力为 0%。

### 1.5 真实产品链路基本连通

Human50 当前通过 49/50，Gate8 本轮 9/9 并通过 Live Provider Smoke，说明 CLI、REPL、Skills、多 Agent、恢复和安全链路大部分能够真实运行。

## 2. 当前不能直接推出的结论

| 现有数据 | 不能直接推出 |
|---|---|
| 12 个固定任务 100% | 任意代码仓库任务都能 100% 完成 |
| Prefix Cache 命中率 85.3% | 本轮所有 DeepSeek 请求都达到相同命中率 |
| Prompt 字符下降 | Provider 账单按相同比例下降 |
| Memory Recall@K 100% | 模型总会正确使用记忆 |

| 安全事件被记录 | 最终文件或 Memory 一定没有副作用 |

## 3. 已发现的主要局限

### 3.1 Harness Benchmark 业务复杂度有限

12 个任务适合验证合同，但编辑目标和 Workspace 规模较小。多文件重构、依赖升级、复杂测试失败和长时间任务仍覆盖不足。

### 3.2 前缀缓存实验尚未统一复现

85.3% 来自独立实验，本轮完整评测没有重新聚合。需要固定请求序列、Provider Usage 字段和自动报告，形成一条可重复运行的证据链。

### 3.3 Live Memory 没有体现工具效率收益

离线消融将重复读取从 60 次降到 0 次，但 DeepSeek Live 的 `memory_on` 重复读取高于 `memory_off`。这说明问题已从“能否召回”转向“模型是否信任和使用记忆”。

### 3.4 LLM Handoff 尚无稳定总成本收益

Handoff 的 Verifier 通过率优于 Compact，未缓存输入中位数也下降，但平均总输入 Token 上升 4.26%，当前不能宣称稳定的总成本下降。

### 3.5 S45 存在安全状态一致性缺口

Human50 的唯一失败说明 Secret 拒绝决策与最终存储状态仍需统一。该问题比单纯提高场景通过率更重要，因为它关系安全不变量是否真正落地。

### 3.6 业务 Dogfood 样本仍小

当前 3 个场景适合发现集成问题，但不足以估计真实业务成功率，也缺少多轮需求变更和更大型代码仓库。

## 4. 后续增强优先级

### P0：修复 S45 并完整回归

```text
定位拒绝事件与最终 Memory 不一致
        |
        v
增加最小确定性回归用例
        |
        v
单独重跑 S45
        |
        v
完整重跑 Human50
```

验收标准：Secret 拒绝事件、返回结果和最终存储状态三者一致，且其他 49 个场景无回归。

### P1：优化真实模型的记忆使用

- 在记忆条目中提供来源、时间和 Workspace 新鲜度证据。
- 区分“已有可靠记忆”和“必须重新读取验证”的场景。
- 对重复读取建立明确 Trace 指标。
- 使用同任务配对实验验证读取次数、工具步数和正确率。

### P1：建立可重复的 Prefix Cache Benchmark

- 固定稳定前缀与动态后缀序列。
- 保存缓存命中 Token、未缓存 Token 和请求次数。
- 对比稳定布局与扰动布局。
- 只有实际采集到对应字段时，才报告命中率、TTFT 和 Provider Usage。

### P2：扩展复杂真实任务

- 多文件重构与测试修复。
- 依赖升级和配置迁移。
- 测试失败后的诊断与二次修改。
- 长会话需求变更。
- 多 Agent 并发与写入冲突。

### P2：建立版本趋势

按 Git Commit 和模型版本持续记录：任务与 Verifier 通过率、P50/P95 工具步数和耗时、Provider Usage、缓存命中、失败类型和版本差异。

---

## 5. 面试中的最佳结论表达

> “我没有把所有评测揉成一个总分，而是分成确定性 Harness 回归、模块消融、真实模型矩阵和真人场景验收。当前可以确认运行时合同、上下文正确性、记忆召回安全和恢复漂移识别有效；同时 Live Memory 没有降低重复读取、LLM Handoff 没有形成稳定总 Token 收益，Human50 还有一个 Secret 存储一致性失败。这些反例帮助我确定下一步优先级：先修复 S45 并完整回归，再优化模型使用记忆的策略和可重复的 Prefix Cache 实验。”

---

## 6. 维护规则

1. 先更新任务与 Verifier。
2. 再更新机器可读产物 Schema。
3. 运行确定性回归和相关专项实验。
4. 重大运行时变更后执行 Live 与真人验收。
5. 最后更新 `docs/metrics/` 的结果快照和本模块结论。

文档与代码发生冲突时，以当前代码、原始运行产物和可复现结果为准。
