# 01. Pico 评测目标与分层方法

> **评测哲学**：评测的核心不是“跑了多少测试”，而是针对每项关键能力提出可证伪的问题，并用恰当的环境、严格的对照组与不可篡改的工程证据回答它。

---

## 1. 被测对象与变量隔离

Pico 的被测对象包含两部分，必须通过科学实验设计将二者隔离：

| 被测对象 | 主要变量 | 典型失败场景 | 隔离与验证手段 |
| :--- | :--- | :--- | :--- |
| **模型能力 (Model Agent)** | 语言理解、推演规划、工具选择、代码生成 | 选错工具、遗漏约束、逻辑推理中断 | 采用 L4 Live Provider 矩阵与端到端任务测试。 |
| **Harness 框架 (Agent Harness)** | 状态机、工具网关、上下文编排、记忆治理、恢复 | 越权执行、状态丢失、压缩误删、死锁卡死 | 采用 L2 确定性回归测试，使用 `FakeModelClient` 锁定模型输入输出。 |

* **为什么必须分层？**：如果只运行真实大模型，失败可能来自 API 网络抖动或模型随机性，无法证明是 Harness 代码出了 Bug；如果只使用 Mock，又无法证明真实大模型能正确配合 Harness 机制。因此 Pico 建立了 L1 ~ L4 四层评估演进。

---

## 2. 六项核心能力与可证伪问题

```text
┌────────────────────────────────────────────────────────┐
│ L1 静态质量与单元测试 (Pytest / Ruff / Type Hints)      │
└───────────────────────────┬────────────────────────────┘
                            ▼
┌────────────────────────────────────────────────────────┐
│ L2 Harness 确定性回归 (FakeModelClient / 固定痕迹)       │
└───────────────────────────┬────────────────────────────┘
                            ▼
┌────────────────────────────────────────────────────────┐
│ L3 模块消融与专项挑战 (Context / Memory / Recovery)      │
└───────────────────────────┬────────────────────────────┘
                            ▼
┌────────────────────────────────────────────────────────┐
│ L4 Live Provider 与真人场景 (DeepSeek V4 / Gate8 / Human50)│
└────────────────────────────────────────────────────────┘
```

### 2.1 Agent Harness 执行可靠性
* **验证点**：模型响应经解析、Schema 校验、执行、状态更新和完成门禁后，产生正确且可审计的结局。
* **可证伪问题**：当参数错误、路径逃逸或连续重复调用发生时，Agent Harness 是否能在限步内阻断、引导并成功恢复？
* **衡量证据**：`report.json`、`trace.jsonl` 中的 `stop_reason` 与 `tool_steps`。

### 2.2 上下文完整性与资源效率
* **验证点**：字节级稳定前缀 Header、工具长结果落盘 (Artifact Offloading) 与阶梯剪枝是否在节省 Token 的同时维持关键信息。
* **可证伪问题**：在 Prompt 字符大幅压缩后，当前 Task 请求、关键故障证据与安全约束是否无损保留？
* **衡量证据**：Prompt 字符压缩率、E2E 输入 Token 下降率与前缀缓存（Prompt Caching）命中率。

### 2.3 跨会话分层记忆能力
* **验证点**：长期事实能否被精准召回、覆盖更新（`supersede`）、过期失效（`stale_evidence`）与安全拦截（`quarantine`）。
* **可证伪问题**：召回正确证据是否真正转化为更高的答对率与更少的重复文件读取？
* **衡量证据**：`Evidence Recall@K`、`Accuracy`、`Poison Quarantine Rate`。

### 2.4 任务中断恢复能力
* **验证点**：Agent 发生中断后，能否依据当前的 Workspace 指纹重新校验旧状态并续接。
* **可证伪问题**：当 Checkpoint 与磁盘现实不一致时，系统是会自动重新锚定还是错误接受旧结论？
* **衡量证据**：`resume_status`、首动作正确率、`workspace_drift` 识别率。

### 2.5 运行时与数据治理安全
* **验证点**：高危工具调用、沙箱路径逃逸、包含密钥的恶意记忆与 Prompt Injection 是否被 100% 阻断。
* **可证伪问题**：系统是仅记录了“拦截事件”，还是确保最终文件与记忆状态在磁盘层均未受污染？
* **衡量证据**：`security_event_type`、磁盘落盘核查。

### 2.6 真实任务端到端完成能力
* **验证点**：上述 Harness 机制组合后，在真实 API Provider 下的综合可用性。
* **可证伪问题**：离线测试中的机制优势，能否在真实 DeepSeek V4 调用中保持？
* **衡量证据**：`Human50` 场景通过率、`Gate8` 门禁通过率。

## 3. 四层评测的职责与代码映射

| 评测层 | 验证职责 | 核心代码/脚本实现 | 调用真实模型？ | 主要判定证据 |
| :--- | :--- | :--- | :---: | :--- |
| **L1 静态单元测试** | 校验函数边界、Schema 解析与基础逻辑 | `tests/test_*.py` | 否 | Pytest 结果、Ruff 校验 |
| **L2 Harness 回归** | 验证控制循环、8重工具网关与状态机 | `tests/test_pico.py` | 否 (`FakeModelClient`) | `trace.jsonl`、`report.json` |
| **L3 模块消融与挑战** | 验证上下文压缩、记忆召回与恢复因果收益 | `pico/evaluation/` <br> `context_eval.py`<br>`memory_agent_eval.py` | 部分 | `Recall@K`、`poison_quarantine_rate` |
| **L4 Live 真实验收** | 端到端真实 API 交互、真人场景验收 | `scripts/run_*_gate.py` | **是 (DeepSeek V4)** | 场景检查项、`Workspace` 结果、`Trace` |

## 4. 确定性程序 Verifier vs LLM Judge

Coding Agent 的许多产出具备天然的**确定性物理真值**（如文件是否改动、测试是否通过、路径是否逃逸、敏感 Key 是否写盘）。

Pico 坚决放弃模糊且易随模型版本漂移的 “LLM Judge”，全面采用**程序确定性 Verifier**：

```text
用户请求 / Task
      │
      ▼
Agent 执行轨迹 ─────────► Trace 结构事件与状态转移校验 (Trace Verifier)
      │
      ▼
Workspace 物理改动 ──────► Git Diff / AST 校验 (Workspace Verifier)
      │
      ▼
单元测试 / 编译器 ──────► 自动化 pytest / Exit Code 校验 (Execution Verifier)
```

通过确定性程序 Verifier，消除了评测裁判本身的不确定性，确保评测结果 100% 可复现与可信。
